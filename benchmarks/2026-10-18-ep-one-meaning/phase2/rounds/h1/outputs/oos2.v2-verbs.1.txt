No, I don't agree. The two sprints are already spent whether you keep the cache or not, so they shouldn't count in the decision. What matters is the cost from here on. Keeping the cache means you maintain more code, carry more bug risk, and get worse performance than the standard library map. Deleting it removes all three.

Before you delete it, check two things:

1. **Is the benchmark valid?** Make sure it uses realistic key sizes, access patterns, concurrency, and hit rates. Also check that it's measuring the cache and not warm-up or allocation noise. If the benchmark is wrong, the result is wrong in either direction.
2. **Does the cache do something the plain map doesn't?** Examples are eviction (LRU or size bounds), TTL expiry, or safe concurrent access. If you need those, compare against a maintained library that provides them before you decide to keep your own. If you don't need them, a plain map is enough.

If both checks come back clean, replace the cache with the standard map and delete the custom code. Don't keep it around "for later". Git history keeps it if you ever need it back, so deleting loses nothing.

The two sprints weren't wasted if you learned the workload doesn't need a custom cache. Keep the benchmark. It tells you if the answer changes later, for example if the workload grows or you need eviction.
