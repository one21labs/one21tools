```markdown
# Config Subsystem: Completion Plan

## Problem and success criteria
The one consuming team needs the CLI to read `config.json` at startup and validate
`api_url`, `team_id`, `log_level`.

Done when:
- [ ] CLI loads `config.json` at startup via the JSON adapter
- [ ] Each of the three fields is validated, with a clear error naming the field and
      the reason (missing, wrong type, invalid value)
- [ ] Invalid config exits non-zero before the CLI does any other work
- [ ] The consuming team has run it against their real config

## Current state
| Component | State |
|---|---|
| JSON adapter | Finished |
| Field validation (3 fields) | TO CONFIRM: not stated as done |
| YAML / TOML / XML adapters | Scaffolded, unfinished |
| Hot-reload watcher | Half wired |
| Migration framework | Interfaces only |

## Phase 1: Ship the requirement (this sprint, blocking)
1. Confirm or implement validation for the three fields. Allowed values for
   `log_level` and the format of `api_url` and `team_id` are defined once, in one
   schema or constants module, and not repeated elsewhere.
2. Wire startup load → validate → fail fast.
3. Tests: valid config; each field missing; each field wrong type; each field invalid
   value; malformed JSON; file not found.
4. Hand to the consuming team and get sign-off.

Phase 1 is the sprint deliverable. Nothing below blocks it.

## Decision gate (before any Phase 2-4 work)
For each optional feature, write down who asked for it and what they need it for.
If there is no named consumer, the feature stays parked. Parked means the scaffolding
stays in a clearly marked branch or directory, is not wired into the CLI, and is not
maintained.

| Feature | Named consumer? | Go / Park |
|---|---|---|
| YAML adapter | | |
| TOML adapter | | |
| XML adapter | | |
| Hot reload | | |
| Migrations | | |

## Phase 2: Remaining adapters (only those with a named consumer)
Per adapter:
- Implement the adapter interface; parse to the same internal model the JSON adapter produces
- The same three-field validation runs after parsing and is not reimplemented per format
- Tests: a shared adapter conformance suite run against every format, plus per-format
  malformed input
- Format detection: by file extension, with an explicit error for unknown extensions
- XML needs a decision on attributes versus elements and on how types are inferred,
  because XML has no native types. Decide this before implementation.
- Done when: the same logical config in each format yields an identical validated result

## Phase 3: Hot reload (only with a named consumer)
Open design questions to answer first:
- Which settings may change at runtime, and which need a restart? (`api_url` mid-run?)
- Behavior when the new file is invalid: keep the last good config and log the error
  (recommended) or crash
- Debounce for editors that write temp-file-then-rename or write multiple times
- Watcher lifecycle: start, stop, clean shutdown, no leaked handles
Then: finish wiring, add tests (valid change, invalid change, rapid successive writes,
file deleted and recreated), and write down the reload semantics.

## Phase 4: Migrations (only with a named consumer)
Precondition: at least two real config versions exist. With only v1 there is nothing to migrate.
- Define the version field and where it lives in the file
- Implement migration steps v(n) → v(n+1), applied in order
- Decide: migrate in memory only, or rewrite the file (recommended: in memory only,
  with an explicit command to rewrite)
- Tests: each step; a chain of steps; unknown future version; missing version field
- Done when: an old-version fixture loads and validates

## Risks
- Scope: Phases 2 to 4 are three independent pieces of work, each with design
  questions still open. Estimate each after the decision gate.
- Maintenance: every adapter and subsystem kept in the tree needs ongoing tests and fixes.
- Duplication: validation and format-specific rules must stay in one place each.
```
