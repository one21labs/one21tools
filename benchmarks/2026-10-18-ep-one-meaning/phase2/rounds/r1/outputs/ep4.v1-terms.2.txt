Nobody has asked for YAML, TOML, XML, hot reload or migrations, and finishing them this sprint would put the real requirement behind speculative work. The two weeks already spent are gone whether or not you finish these pieces. The only question is what the next sprint's time buys. So the plan ships the requirement first. It keeps the three components as a costed backlog, each waiting on a named requester, so you can start one the day someone asks.

```markdown
# Config Subsystem: Completion Plan

## 1. Problem and success criteria
Requirement (from the one consuming team): at startup, read `config.json` and
validate `api_url`, `team_id`, `log_level`.

Done when:
- [ ] The CLI loads `config.json` at startup and exits non-zero with a message
      naming the field and the problem if validation fails.
- [ ] All three fields are validated (rules in section 3).
- [ ] The consuming team has run it against their real config and signed off.

Out of scope this sprint: YAML/TOML/XML, hot reload, schema migration.

## 2. Current state
| Component | State | Requested by |
|-----------|-------|--------------|
| JSON adapter | Finished | The requirement itself |
| Adapter architecture | Built | Nobody |
| YAML / TOML / XML adapters | Scaffolded | Nobody |
| Hot-reload watcher | Half wired | Nobody |
| Migration framework | Interfaces only | Nobody |

## 3. Design for the actual requirement (blocking decisions)
These are open. Resolve them before building.
- [ ] `api_url`: allowed schemes (https only?), must it be reachable at startup?
- [ ] `team_id`: type and format (string/int, pattern, length)?
- [ ] `log_level`: allowed values. Define them ONCE (single constant or enum)
      and have validation and help text refer to it.
- [ ] Required vs optional per field; defaults, if any.
- [ ] Unknown extra fields: reject, warn, or ignore?
- [ ] Config file location: fixed path, flag, or env var? Behavior if missing.
- [ ] Error contract: message format, exit code, report all errors or first only.
- [ ] Ask the consuming team to confirm the answers above.

## 4. Tasks (this sprint)
1. Resolve section 3 with the consuming team (decision task, first).
2. Write the validator for the three fields against the JSON adapter.
3. Wire load and validate into CLI startup, with the error contract.
4. Tests: valid config, each field missing, each field invalid, malformed JSON,
   missing file. Include a check that the failure path exits non-zero.
5. Run against the team's real config; get sign-off.
6. Freeze the unused scaffolding: leave it in a clearly marked directory or
   branch, not on the startup path. Do not delete it yet.

## 5. Deferred backlog (start only when a named requester exists)
Each item has a gate: a person or team who asked, and the use case.

| Item | Gate | Remaining work (rough) |
|------|------|------------------------|
| YAML adapter | A team needs YAML | Parser, same validator, tests, error mapping |
| TOML adapter | A team needs TOML | Same |
| XML adapter | A team needs XML | Same, plus decide the mapping of attributes and elements to fields |
| Hot reload | A user needs live config changes | Finish watcher wiring, define behavior on invalid reload (keep the old config), debounce, tests |
| Migrations | A second config schema version exists | Implement the interfaces, version field, upgrade path tests |

Rules for the backlog:
- Adapters reuse the single validator. No per-format validation copies.
- Do not carry upkeep cost for code with no user: if nothing is requested by
  the review date below, delete the scaffolding (git keeps it).
- Review date: end of next sprint.

## 6. Risks
- Unused scaffolding drifts from the validator and the JSON path, and grows
  maintenance cost with no benefit.
- Team may later ask for a format. Mitigation: the adapter interface exists,
  so adding one is a bounded task (see backlog).
```
