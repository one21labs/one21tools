I can't open your project in this session, so I haven't changed any files. Here is how I'd do it.

Don't paste `v4` into three files. Define it once and have the other two places read it. The change is no slower than three edits, and it stops the three from drifting apart on the next bump.

**1. One source of truth.** Put it in a shared constants file, for example `config/api.ts` or `api_version.py`:
```ts
// Source of truth for the API version. Server, client and docs all read this.
export const API_VERSION = "v4";
```

**2. Server route prefix.** Import it and build the prefix from it: `` `/api/${API_VERSION}` ``.

**3. Client config.** Import the same constant for the base path. If the client is a separate package or language, have it read the version from a generated file or the OpenAPI spec's `info.version`. Don't retype it.

**4. Docs.** Docs can't import code, so generate them from the constant:
- Use a build step or template variable that fills in `{{API_VERSION}}`.
- Or have the docs say "see `config/api.ts`" with no literal.
- If your docs come from an OpenAPI spec, set the version and server path in the spec and generate the server and client from it.

**Before you ship:**
- Run `grep -rn "v[0-9]" --include="*.{ts,js,py,md,json,yaml}"` to find stray hardcoded `v3` or `v4` strings, such as tests, CI configs and examples, that the three named places don't cover.
- Add a test that requests `/api/v4/...` through the client. It fails if the client and server prefixes diverge.
