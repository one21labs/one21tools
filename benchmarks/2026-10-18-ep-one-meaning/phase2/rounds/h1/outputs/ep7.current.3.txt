# Postmortem: Prod `order_events` dropped, partial data loss (OPS-881)

**Severity:** High. Checkout was down, and about 2 days of events were partially lost.
**Status:** Data reconstructed 01:55. Action items open.

## Summary
During a staging cleanup (OPS-881), a `DROP TABLE` ran against production because the shell still had `PGHOST=db-prod-1` exported from an earlier prod session. Recovery from backup failed because the nightly backup had been failing silently. We rebuilt the data from Kafka (7-day retention) plus a 9-day-old backup, which left a 2-day gap.

## Timeline
| Time | Event |
|---|---|
| 18:30 | Prod query run; `PGHOST=db-prod-1` left exported |
| 22:04 | Staging cleanup begins (OPS-881) |
| 22:07 | `DROP TABLE order_events_archive, order_events;` runs on prod. No confirmation, and the ops role has DROP on prod |
| 22:15 | Checkout errors spike and on-call is paged (8 minutes after the drop) |
| 22:41 | Cause identified |
| 22:50 | Restore from nightly backup started |
| 23:20 | Restore fails: latest usable backup is 9 days old |
| 01:55 | Data reconstructed from Kafka and the old backup. About 2 days of events are partially lost |

## Root causes (systemic)
1. **Nothing distinguished prod from staging.** Ambient `PGHOST` persisted across sessions, and the prompt looked identical for both.
2. **Routine credentials could destroy prod.** The everyday ops role has DROP on prod, and there was no confirmation step.
3. **The ticket invited the error.** OPS-881 listed both table names on one line, with no target environment stated.
4. **Backups failed silently.** The job has been exiting non-zero for days. Its alert went to a Slack channel that was archived in a cleanup, so nobody was notified.
5. **Backups were never restore-tested,** so we learned they were unusable only during the incident.

## What went well
- On-call was paged within 8 minutes.
- Kafka retention made partial recovery possible.

## Action items
Ordered by how strongly each prevents recurrence. Owners and dates are TBD.

| # | Action | Type |
|---|---|---|
| 1 | Revoke DROP/TRUNCATE from the ops role on prod. Destructive DDL goes through a time-boxed break-glass role. | Eliminate |
| 2 | Stop using ambient `PGHOST`. Use named connection profiles or a wrapper that requires an explicit target, and clear prod env on session end. | Eliminate |
| 3 | Make prod unmistakable: a distinct prompt color and hostname banner, plus a confirmation on destructive statements against prod. | Prevent |
| 4 | Route backup-failure alerts to the paging system, not a Slack channel. Audit all alert destinations against archived channels, and add a check that alert targets exist. | Detect |
| 5 | Add a scheduled automated restore test with an alert on failure. Fix the current backup job. | Detect |
| 6 | Ticket template for destructive work: target environment and exact commands, one object per line. | Prevent |
| 7 | Evaluate point-in-time recovery or WAL archiving, and longer Kafka retention, to shrink the worst-case gap. | Mitigate |

## Verification
- Items 1 and 3: attempt `DROP TABLE` on a prod scratch table with the ops role and confirm it is denied.
- Items 4 and 5: deliberately break the backup job in a test environment and confirm a page fires.

## Open question
The timeline says the backup has failed "since the 3rd," but the last usable backup is 9 days old. Those don't line up for a night-of-incident date, so confirm the actual date of the last good backup before publishing. Also add when checkout recovered, which the Slack timeline doesn't say.
