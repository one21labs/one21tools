## 4. Analysis

### 4.1 Problem statement (facts only)

The export job delivered a zero-row file to a client with exit code 0 and no alert.

### 4.2 Five Whys, branched

**Branch A: why did an empty file exist?**
1. Why was the file empty? The edited query returned no rows.
2. Why did a broken query reach production? It was not run once by hand before
   deploy. The wiki says to do this.
3. Why was the step skipped? It is a manual step that lives in a wiki. An engineer
   six weeks in had no forcing function to find it or follow it.
4. Why is nothing else catching a bad query? Nothing in the pipeline checks the
   output. The only check is a human remembering.
5. **Root cause A:** correctness of the export depends on a manual, unenforced step.

**Branch B: why did an empty file get delivered?**
1. Why was an empty file delivered? Delivery ships whatever file the job wrote.
2. Why? Delivery is gated only on exit code 0.
3. Why was exit code 0? The job treats "ran without throwing" as success. A
   zero-row result is not an error, and in the credential case the error was
   swallowed.
4. **Root cause B:** the job's definition of success (exit 0) is not the
   definition of the outcome we owe the client (a valid, non-empty file).
   Delivery is not gated on output validity.

**Branch C: why did nobody find out?**
1. Why no alert? Monitoring checks only the exit code.
2. Why? Monitoring asks "did the process finish?", not "did the output meet
   expectations?"
3. **Root cause C:** no check exists on the output itself, before or after delivery.

### 4.3 Why this is one problem, not three

The three incidents had three different triggers (schema rename, swallowed
credential error, unverified query change). A fix aimed at any single trigger
(for example, "remind people to run the query") would not have stopped the other
two. All three succeeded through the same gap: **nothing between "job exits 0"
and "client receives file" checks that the file is good.** The trigger varies;
the gap does not. That gap is the root cause to fix.

### 4.4 What this is not

This is not "human error by Priya." Priya followed the path the system offered.
The system made it possible to ship an unverified query and had no other defense.
A correct manual step, written only in a wiki, will be missed again by the next
new joiner, or by a veteran on a busy night.

| B | Success = exit 0; delivery not gated on output validity | All 3 incidents |

## 6. Changes

Ranked: remove > prevent > detect. Do B first. It alone would have stopped all
three incidents.

### 6.1 Remove (eliminate the way the failure happens)

1. **Delete the "empty output is success" path.** The job must fail (non-zero
   exit) when it writes zero rows, unless the export is explicitly configured to
   allow empty results (see open question 1).
2. **Remove the swallowed-exception path.** Credential and connection errors must
   propagate and fail the job. Audit the job for other broad catch-and-continue
   blocks.
3. **Remove the manual wiki step as the control.** Once 6.2 is live, delete the
   step from the wiki. The check lives in code, not in a doc, so the code is the
   single source of truth and the wiki cannot drift from it. Do not leave a
   history note in the wiki; git history holds that.

### 6.2 Prevent (block bad output from reaching the client)

1. **Add a validation gate between "file written" and "file delivered."** Delivery
   happens only if validation passes. Checks:
   - Row count > 0.
   - Row count within a tolerance of a trailing baseline (for example, not below
     X% of the trailing 14-day median). TODO: choose the threshold with the data
     owner.
   - Expected columns present, in the expected order and types (catches the
     schema-rename case).
2. **Put thresholds and expectations in one config file per export** (single
   source of truth). The job, the gate and the alert all read it. Do not
   hard-code numbers in several places.
3. **Run the same gate on query changes in CI.** A changed export query runs
   against a representative dataset or staging, and the gate must pass before
   merge. This replaces the manual "run it once by hand" step with an enforced one.

### 6.3 Detect (when prevention fails)

1. **Alert on output, not exit code.** Page or notify when the gate fails, when
   no delivery occurred by the expected time, or when delivered row count
   deviates from baseline.
2. **Add a dead-man check.** Alert if no valid delivery is recorded by the
   expected time, so a job that never runs or never reaches the gate is also caught.
3. **Record row count and file size per run** as metrics so trends are visible.
