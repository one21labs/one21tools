## Rationale and details

### 1. Setup steps
- The two copies disagree (`npm install` vs `npm ci`, copy `.env.example` vs

  produces.
- README is the canonical home because it is the first file a new person reads.
- Keep README's `npm run dev` and `.env.example` copy. Your own history says
  `npm start` was retired in favour of `npm run dev`, and copying
  `.env.example` is less error-prone than writing `.env` by hand.
- Open item: `npm install` vs `npm ci` is undecided. Before finalizing, check
  package.json and the lockfile. If the team wants reproducible installs, README
  should say `npm ci`. Make that edit once, in README only.
- CONTRIBUTING keeps only a pointer such as "Setup: see README.md#setup".

### 2. Timeout
- Neither doc is trustworthy. They disagree with each other, and nothing shows
  that either matches the code.
- The constant in src/http/client.js is the truth. Docs must not restate its
  value, because any number in prose becomes a stale copy.
- Delete the sentence from both files. If a reader needs the value, the
  constant's name in that file is the answer. If a doc must mention the
  behaviour, it names the file path only.
- Open item: read the constant and confirm neither doc was right. This does not
  change the plan, but any user-facing claim about timeouts should be checked

### 3. Support email

  for contact information.

### 4. billing.js rule

  CLAUDE.md loads in every session, so the rule would cost context everywhere

## Prevention

- Docs never state values defined in code (timeouts, ports, limits). They
