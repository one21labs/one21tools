The one team that uses the tool needs only `config.json` read at startup with three fields validated. The two weeks are already spent whether or not you finish the rest. What matters is what the remaining sprint time buys, and finishing three unrequested features buys nothing the team asked for. So the plan ships the requirement first. It then gates each extra feature on a named consumer, so you can still complete them if that holds.

```markdown
# Config Subsystem: Completion Plan

## Problem and success criteria
Requirement (from the only consuming team): read `config.json` at startup and
validate `api_url`, `team_id`, `log_level`.

Done when:
- [ ] Startup loads `config.json` and fails fast with a clear message per invalid field
- [ ] Validation rules for the three fields are defined once (single schema) and
      every adapter and consumer references it
- [ ] Tests cover: missing file, malformed JSON, missing field, wrong type,
      invalid `log_level`, invalid `api_url`
- [ ] The consuming team confirms it works against their real config

Out of scope until a consumer exists: anything below marked "gated".

## Phase 0: Ship the requirement (sprint-critical, do first)
1. Define the schema for the three fields in one module (SSoT). Specify:
   `api_url` (valid URL, scheme allowed?), `team_id` (type, format),
   `log_level` (enum of allowed values).
2. Wire the finished JSON adapter into startup through that schema.
3. Error handling: one message per field, non-zero exit, no partial config.
4. Tests per the list above. Run against the team's actual config.
5. Release to the consuming team and collect feedback.

Estimate: a few days at most, since the JSON adapter already exists.

## Decision gate (before Phase 1)
For each item below, record: who asked for it, what they will do with it, and
how we will know it worked. If the answer is "nobody / no one", the item is
deferred, not cancelled. Its scaffolding stays in place and the cost of
finishing it later is unchanged.

| Item | Named consumer? | Success criterion | Decision |
|------|-----------------|-------------------|----------|
| YAML adapter | TBD | TBD | |
| TOML adapter | TBD | TBD | |
| XML adapter | TBD | TBD | |
| Hot reload | TBD | TBD | |
| Schema migrations | TBD | TBD | |

## Phase 1 (gated): Remaining adapters
Only for formats with a named consumer.
- Each adapter implements the existing adapter interface and returns the same
  normalized structure; validation always runs through the Phase 0 schema.
- Shared adapter conformance test suite: same fixture expressed in each
  format must yield an identical validated result.
- XML needs a decision first: how attributes/elements map to the three
  scalar fields (this ambiguity is why it is the riskiest adapter).
- Format detection: by file extension or explicit flag? Decide once.
- Exit: conformance suite passes; the requesting team verifies.

## Phase 2 (gated): Hot reload
Prerequisite question: what long-running process reloads config? A CLI that
reads at startup does not.
- Finish wiring the watcher only if a long-running mode exists.
- Define behavior on invalid reload: keep last-known-good config and log the
  error (never apply a partial or invalid config).
- Debounce rapid file writes; handle editor atomic-save (rename) patterns.
- Tests: valid change applied, invalid change rejected, rapid writes, file
  deleted and recreated.
- Exit: demonstrated against the real long-running consumer.

## Phase 3 (gated): Schema migrations
Prerequisite: a second schema version must exist. With one version there is
nothing to migrate.
- Define the version field location and the behavior when it is absent
  (treat as v1).
- Implement migrations as ordered, pure `vN -> vN+1` functions with tests
  using real old-format fixtures.
- Decide failure behavior: refuse to start on an unknown or future version.
- Exit: a real v1 -> v2 change migrates correctly end to end.

## Risks and unknowns
- Unused code carries ongoing cost: each adapter and subsystem adds tests,
  docs, and maintenance for zero current users.
- Half-wired watcher: decide whether to leave it disabled behind a flag or
  remove it from the startup path so it cannot affect Phase 0.
- Scope drift: the gate table above is the control; revisit it each sprint.

## Verification
- Phase 0: inject each failure case (bad URL, missing field, bad log level)
  and confirm startup exits with the expected message.
- Later phases: each has its own exit criterion above, tested against its
  named consumer.
```
