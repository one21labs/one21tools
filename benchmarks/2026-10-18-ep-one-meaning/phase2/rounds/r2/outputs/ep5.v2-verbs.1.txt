The PM's approval tells us who agreed, but the plan never states several things the build depends on. I've listed each as a decision task ahead of the build tasks and left every answer open. Most of them are quick conversations, and each one blocks specific build work.

```markdown
# User Data Export: Implementation Tasks

Approved plan (verbatim): "User Data Export feature: build an API endpoint that exports all of a user's data. Use whatever format is easiest. Should be fast. Ship next week."

## Phase 0: Decisions (these block the build tasks that name them)

Each task needs a named owner and a written answer, recorded here once and referenced by the build tasks.

- [ ] D1. Data scope: what does "all of a user's data" include? (Which stores and tables, derived data, audit logs, soft-deleted records, data held by third parties, other users' data inside shared objects.) Blocks: B2, B3
- [ ] D2. Output contract: what is the format, the schema, and who consumes the export (the user, support, a compliance request)? "Easiest" is not yet a contract. Blocks: B3, B4
- [ ] D3. Success criteria for "fast": what is the measurable target (latency, maximum export size, expected concurrent requests)? This also decides whether delivery is synchronous or asynchronous. Blocks: B4, T3
- [ ] D4. Authorization: who may export whose data, and how is that verified? Blocks: B1
- [ ] D5. Security and privacy: how are sensitive fields handled (credentials, tokens, PII of other people)? Is an audit log of exports needed? Is there a legal or compliance driver such as GDPR or CCPA? Blocks: B2, B5
- [ ] D6. Error handling: what does the caller see on partial failure, timeout, or an unknown user? Blocks: B4
- [ ] D7. Abuse limits: is there a rate limit or a quota per user? Blocks: B6
- [ ] D8. Delivery and retention: is the export returned in the response or stored somewhere? If stored, who can read it and how long does it live? Blocks: B4, B5
- [ ] D9. Rollout and rollback: is there a feature flag, and what triggers a rollback? Also confirm what "ship next week" means (date, and what must be in it). Blocks: R1
- [ ] D10. Ownership: who maintains this endpoint after launch? Blocks: R2

## Phase 1: Build (after the decisions they reference)

- [ ] B1. Endpoint skeleton and authorization check (D4)
- [ ] B2. Data registry: one definition of which data sources are exportable and how each is read, used by the exporter and by tests. This is the single source of truth for scope. (D1, D5)
- [ ] B3. Serializer for the chosen format, with the schema defined once in one place (D1, D2)
- [ ] B4. Export execution and delivery path, with the error behavior from D6 (D2, D3, D6, D8)
- [ ] B5. Sensitive-field handling, export audit logging, and retention enforcement (D5, D8)
- [ ] B6. Rate limiting or quota (D7)

## Phase 2: Verify

- [ ] T1. Tests per data source in the registry: the export contains exactly the in-scope data for the user and nothing from other users
- [ ] T2. Authorization tests: another user's request, an unauthenticated request, and an unknown user are all rejected
- [ ] T3. Performance test against the target from D3, using a realistically large account
- [ ] T4. Failure tests: a data source down, a timeout, and an oversized export behave as D6 specifies
- [ ] T5. Compare the measured results to the predictions from D3 and record any gap

## Phase 3: Release

- [ ] R1. Feature flag, rollout, and rollback steps (D9)
- [ ] R2. API documentation generated from the code or schema, plus a named owner and on-call notes (D10)
```
