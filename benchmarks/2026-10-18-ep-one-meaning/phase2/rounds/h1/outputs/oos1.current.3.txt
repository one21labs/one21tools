I can't open your project in this session, so I haven't changed any files. Here is how I'd do it, so the three can't drift apart again.

**Define `v4` once and have the other three read it.** Pasting the literal into three files is the cause of the mismatches. A single constant plus three references takes no longer, so it won't slow the ship.

1. **Source of truth:** one file, for example `config/api.(ts|py|json)`, containing `API_VERSION = "v4"`. Mark it as the SSoT in a comment.
2. **Server route prefix:** build it from the constant, e.g. `prefix = f"/api/{API_VERSION}"`, instead of a literal `/api/v4`.
3. **Client config:** import the same constant. If the client lives in a separate package or repo and can't import it, generate its config from the source file at build time. Don't hand-edit it.
4. **Docs:** generate the version string from the same source, either through the OpenAPI spec or a templated include. If the docs are static markdown, the usual fix is to write the version in one place and have the other pages link to it. A hand-typed `v4` in the docs is the copy most likely to go stale.
5. **Check before shipping:** grep for stray literals with `grep -rnE "\bv[0-9]+\b" docs/ client/ server/` and look for `v3` or any other leftover. Then hit `/api/v4/<some endpoint>` and confirm a 200.

If a build or codegen step is out of scope today, the fallback is to put `v4` in all three by hand and note that the single-definition refactor is still owed. I'd avoid that unless you're truly blocked.
