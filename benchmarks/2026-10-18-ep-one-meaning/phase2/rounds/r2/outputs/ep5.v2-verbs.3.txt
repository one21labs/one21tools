The plan leaves some things unstated, though, so I put those first as decision tasks that block the build tasks. The plan doesn't answer them, and I haven't guessed answers, so each one is a question for the PM or tech lead. Each should take minutes to settle, and the build tasks below depend on them.

```markdown
# User Data Export: Implementation Tasks

Approved plan (verbatim): "User Data Export feature: build an API endpoint that
exports all of a user's data. Use whatever format is easiest. Should be fast.
Ship next week."

## Phase 0: Decisions (blocking; answers go in the design note, T0.8)

- [ ] T0.1 Data scope: which stores/tables count as "all of a user's data"?
      Open: derived data, logs, backups, third-party-held data, data about the
      user that other users own (shared content, messages).
- [ ] T0.2 Output contract: what format(s), schema, and field naming does the
      endpoint return? Who consumes it (end user, support, another system)?
- [ ] T0.3 Success criteria for "fast": what measurable target (latency,
      throughput, max data size), and is it sync or async delivery?
- [ ] T0.4 Authorization: who may export whose data (self only, admin, support)?
      How is identity re-verified?
- [ ] T0.5 Sensitive data handling: which fields (credentials, tokens, internal
      flags, other users' PII) are excluded or redacted? Audit logging needs?
- [ ] T0.6 Error handling and limits: behavior on partial failure, timeouts,
      oversized exports, rate limiting, repeat requests.
- [ ] T0.7 Rollout and rollback: feature flag? Rollback criteria? Owner after ship?
- [ ] T0.8 Write the answers to T0.1-T0.7 as a one-page design note. This is the
      single source of truth the tasks below refer to.

## Phase 1: Build (starts after Phase 0)

- [ ] T1.1 Inventory every data source in scope per T0.1; record each source's
      owner and access path in the design note (refer to it, don't copy it).
- [ ] T1.2 Define the export schema/contract per T0.2 in one place (schema file
      or type), imported by the endpoint and the tests.
- [ ] T1.3 Implement the authn/authz checks per T0.4.
- [ ] T1.4 Implement the data collectors, one per source from T1.1.
- [ ] T1.5 Implement the endpoint: assemble collectors, serialize per T1.2,
      apply redaction per T0.5.
- [ ] T1.6 Implement error handling and limits per T0.6.
- [ ] T1.7 Add audit logging per T0.5.

## Phase 2: Verify

- [ ] T2.1 Contract tests against the T1.2 schema.
- [ ] T2.2 Authorization tests: a user cannot export another user's data.
- [ ] T2.3 Redaction tests: excluded fields never appear.
- [ ] T2.4 Performance test against the T0.3 target with realistic data volume.
- [ ] T2.5 Failure-path tests per T0.6 (partial failure, timeout, oversize).

## Phase 3: Ship

- [ ] T3.1 Document the endpoint (generated from the schema, not hand-copied).
- [ ] T3.2 Roll out per T0.7; confirm rollback works.
- [ ] T3.3 Verify in production: export a test account and compare to T1.1.
```

Phase 0 is the part most likely to cost you time later. "All of a user's data" with a "whatever format" contract and no definition of "fast" means T1.2 and T2.4 can't start. A scope answer that arrives late, such as another data store nobody listed, is the most common reason a feature like this slips past its ship date.
