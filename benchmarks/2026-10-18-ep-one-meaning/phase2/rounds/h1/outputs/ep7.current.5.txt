# Postmortem: Production `order_events` table dropped (OPS-881 cleanup)

**Severity:** High. Checkout was down, and about 2 days of order events were partially lost.
**Duration:** Checkout errors began 22:15. Data was reconstructed by 01:55, about 3h40m later.

## Summary
During a staging cleanup under OPS-881, an SRE ran `DROP TABLE order_events_archive, order_events;` in a shell that still pointed at production. The production `order_events` table was dropped. The nightly backup had been failing silently for days, so the latest usable backup was 9 days old. We rebuilt the data from Kafka (7-day retention) plus that backup, which left a gap of about 2 days of events.

## Timeline
| Time | Event |
|---|---|
| 18:30 | An earlier prod query leaves `PGHOST=db-prod-1` exported in a terminal. |
| 22:04 | Dev starts the OPS-881 staging cleanup. |
| 22:06 | Dev opens a terminal that still has the prod `PGHOST`. The prompt looks identical for prod and staging. |
| 22:07 | Dev runs the DROP. The ticket's script listed both table names on one line, and the intent was to drop only the archive table. There is no confirmation, and the ops role has DROP on prod. |
| 22:15 | Checkout errors spike and on-call is paged. |
| 22:41 | Cause identified. |
| 22:50 | Restore from the nightly backup started. |
| 23:20 | Restore fails. The latest usable backup is 9 days old. |
| 01:55 | Data reconstructed from Kafka plus the old backup. About 2 days of events are partially lost. |

## Root causes
The command was the trigger. Five conditions let one mistake become a data-loss incident:

1. **Prod and staging are indistinguishable in a shell.** The prompt is identical and stale env vars persist across sessions.
2. **Routine access can destroy prod.** The everyday ops role has DROP on production, and nothing asks for confirmation.
3. **The ticket put a prod-critical table next to the staging target.** Both names sat on one line, with no environment stated.
4. **Backup failure was silent.** The job has been failing since the 3rd. Its alert went to a Slack channel that was archived in a cleanup, so nobody was notified.
5. **Restore was never tested.** We found out the backups were unusable in the middle of the incident.

Causes 4 and 5 turned an outage that should have been minutes into data loss. A working backup would have made this a short incident.

## Open questions
- **The backup dates don't line up.** The job has failed since the 3rd, but the latest usable backup is 9 days old. Depending on today's date, those may not match. Someone needs to confirm whether there were also failed or partial backups before the 3rd.
- **Detection took 8 minutes** (22:07 to 22:15) and identifying the cause took another 26. Is there a gap in DDL audit logging or alerting on prod?
- **The lost data still needs reconciling.** Customer and finance impact from the 2 lost days needs an owner.
