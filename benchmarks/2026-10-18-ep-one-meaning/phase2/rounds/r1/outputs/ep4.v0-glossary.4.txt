```markdown
# Config Subsystem Completion Plan

## Problem
The one consuming team needs the CLI to read config.json at startup and
validate api_url, team_id, log_level. Nothing else has been requested.

## Success criteria (this sprint)
- CLI reads config.json at startup via the existing JSON adapter.
- Validates the three fields; each failure names the field and the rule it broke.
- Invalid or missing config exits non-zero with that message.
- Tests cover: valid file, missing file, malformed JSON, and each field
  missing / wrong type / out of range.

## Out of scope this sprint
YAML, TOML, XML adapters; hot reload; schema migrations.

## Phase 1 - Ship the requirement (this sprint)
1. Decide and write down validation rules per field (api_url: absolute
   http(s) URL; team_id: type and format; log_level: allowed set).
   Source of truth: one schema/constants module. Docs refer to it.
2. Implement the validator against that module.
3. Wire startup: load -> validate -> fail fast with clear errors.
4. Tests listed above. Verify by running the CLI against each bad file.
5. Hand to the team; confirm it meets their need.

## Phase 2 - Stabilize the unused scaffolding (this sprint, small)
Goal: the half-built code does no harm and costs nothing to keep.
1. Make sure the YAML/TOML/XML adapters, watcher, and migration
   interfaces are not reachable from the startup path (unregistered or
   behind a build/feature flag), so half-wired code cannot affect users.
2. Add a short note at the adapter registry stating which adapters are
   supported (JSON only). The registry is the source of truth for this.
3. Do not extend or refactor the scaffolding.

## Phase 3 - Optional components (start only when the gate is met)
Each item starts only when a named user or team asks for it. Each needs a
short written design first (problem, interfaces, error handling, success
criteria, how failure is verified).

### 3a. Additional format adapters (YAML, TOML, XML)
- Gate: a team requests that format.
- Build one adapter per request, not all three.
- Design must settle: type coercion into the shared schema, duplicate keys,
  error messages with line numbers.
- Verify: the same fixture content in each format yields identical
  validated output; malformed input produces the same error shape.

### 3b. Hot-reload watcher
- Gate: a user reports needing config changes without restart.
- Design must settle: what happens on an invalid edit (keep last-good
  config and log), partial writes / editor save-rename behavior, which
  consumers see the new values, and whether the CLI is long-running at all.
  Most CLIs are short-lived and never need this.
- Verify: write an invalid file mid-run and confirm the old config stays
  active and an error is logged.

### 3c. Schema migration framework
- Gate: a second config schema version actually exists.
- With one version there is nothing to migrate. The interfaces cannot be
  validated without real v1 -> v2 cases.
- Design must settle: version field location, migration ordering,
  behavior on unknown future versions, and whether to rewrite the file.
- Verify: run a v1 fixture through the migration and compare to the
  expected v2 output; run an unknown version and confirm the error.

## Risks
- Scaffolding code rots while unused. Mitigation: Phase 2 isolation; delete
  it if no gate is met in an agreed period (suggest two quarters).
- Team later wants a format or hot reload. Mitigation: the adapter
  architecture still exists, so Phase 3 is incremental.

## Open decisions for you
1. Which validation rules for each of the three fields (Phase 1.1).
2. Whether to delete or keep the unused scaffolding after the review date.
```
