**Why the plan is different**

- **The requirement is small.** One team needs `config.json` read at startup and three fields validated. The JSON adapter is already finished, so the real requirement is probably a day or two from done.
- **The two weeks are sunk cost.** Finishing YAML, TOML, XML, hot reload and migrations means building three features nobody asked for. Each one adds tests, docs and bugs to maintain.
- **Hot reload and migrations don't fit this tool.** A CLI that reads config at startup and exits has nothing to reload. Migrations need at least two config versions to exist, and there is only one.
- **So the plan ships the requirement first and gates the rest.** I didn't silently drop the three features or silently plan them. The first sprint item is the requirement, and each extra feature is built only if someone asks for it. If you want them finished anyway, that's your call, and Phase 2 says how to do it with the least waste.

```markdown
# Config Subsystem: Completion Plan

## Problem and success criteria
The one consuming team needs the CLI to read `config.json` at startup and
validate `api_url`, `team_id`, `log_level`.

Done when:
- [ ] CLI starts with a valid `config.json` and exposes the three fields
- [ ] Each invalid or missing field exits non-zero with a message naming the field
- [ ] Missing or unparseable file exits non-zero with a message naming the path
- [ ] The consuming team has run it against their real config

Not in scope this sprint: YAML/TOML/XML input, hot reload, schema migration.

## Phase 1: Ship the requirement (this sprint)
Owner: TBD. Estimate: 1-2 days.

1. Write the validation rules (decide with the consuming team, record here once):
   - `api_url`: required; must it be https? valid URL?
   - `team_id`: required; type and format (string/int, pattern)?
   - `log_level`: required or defaulted? Allowed values?
   - Unknown extra fields: reject or ignore?
2. Implement validation on top of the finished JSON adapter. Rules live in one
   place (a single schema/validator module); nothing else restates them.
3. Error handling: one error type carrying field name + reason; CLI maps it to
   exit code and message.
4. Tests: valid file; each field missing; each field invalid; no file; bad JSON.
5. Hand to the consuming team; collect feedback.

## Phase 2: Speculative features (gated, not scheduled)
Each item starts only when a named user asks for it. Until then the
scaffolding stays as-is, unreferenced by the CLI's startup path.

| Feature | Trigger to build | Open questions to answer first |
|---|---|---|
| YAML/TOML/XML adapters | A team needs that format | Which format, which team? (Build only that adapter, ~0.5-1 day each) |
| Hot reload | A long-running mode of the CLI exists | What should running code do on change? Invalid reload: keep old config? |
| Migrations | A second config schema version is actually planned | What changes between v1 and v2? Who owns upgrade of existing files? |

If leadership decides to finish them anyway, do it in this order and
re-estimate after each: (1) the one adapter with a real user, (2) remaining
adapters against a shared adapter test suite, (3) watcher, (4) migrations.
Each needs its own written design (scope, error handling, success criteria)
before code.

## Phase 3: Reduce carrying cost of the unfinished code
- Move the scaffolded adapters, watcher and migration interfaces to a clearly
  marked location (e.g. `experimental/`) or a branch, so the shipped path has
  no half-wired code.
- Ensure nothing in the startup path imports the watcher.
- Git history is the record of the work; no extra documentation needed.

## Risks
- Half-wired watcher in the main tree may behave unexpectedly: verify it is
  not started at CLI startup (Phase 1, step 2).
- Validation rules are unconfirmed with the consuming team (Phase 1, step 1).
```
