# Shared phone validation: design and rollout

## Don't use the strictest rule everywhere

These three copies don't implement the same rule, so this isn't a case of duplicated code.

- **Billing and support** check whether a string is a valid E.164 wire value. Support is billing's 2023 copy plus `.strip()`.
- **Signup** checks whether a string looks like something a person typed.

If you apply the strict regex to signup, `(415) 555-0134` and `415.555.0134` fail. They have no `+` and contain punctuation. That would reject most of your ~4,000 daily mobile submissions.

The loose regex has a second problem. It has no `$` anchor and no `fullmatch`, so `5551234abc` passes. Today, signup validation is nearly meaningless.

The strict regex is also slightly wrong. `$` matches before a trailing `\n`, so `"+14155550134\n"` passes billing and goes to the provider. Use `fullmatch`.

## Design

The shared fact is the definition of a phone number and how to convert user input into it. Put that in one library, `acme-phone`, with two functions that have different jobs.

```python
# acme_phone/__init__.py  (the only place the pattern lives)
_E164 = re.compile(r'\+[1-9]\d{7,14}')

def is_e164(s: str) -> bool:
    """Strict wire-format check. No stripping, no cleanup. For code that sends the value onward."""
    return isinstance(s, str) and _E164.fullmatch(s) is not None

def normalize(raw: str, region: str) -> str | None:
    """Turn user-typed input into canonical E.164, or None if it can't be.
    Postcondition: result is None or is_e164(result)."""
```

- **`region` is required, with no default.** `(415) 555-0134` is only a valid number once you know the country. A hidden default would be a silent assumption.
- **`normalize` always returns something that passes `is_e164`.** That guarantee is the contract between signup and billing.
- **Implementation:** `normalize` could wrap the `phonenumbers` library, which handles national formats, extensions and country rules. A hand-rolled strip-and-prefix works for US-only traffic but breaks as soon as you have international users. This is a decision for you (see the open questions).
- **Error handling:** neither function raises on bad input. `normalize` returns `None` and `is_e164` returns `False`, so callers decide what to do.
- **Versioning:** semver on the private PyPI. A change to what counts as valid is a major version.

How each service uses it:

| Service | Uses | Behavior |
|---|---|---|
| signup | `normalize(raw, region)` | Accepts typed formats and stores or forwards the E.164 result. |
| billing | `is_e164(s)` | Strict. Sends to the provider only what passed. |
| support | `normalize` or `is_e164` | Depends on whether agents type or paste numbers (open question). |

This also fixes a likely data-flow problem. If signup stores raw `(415) 555-0134` and billing later reads it, billing rejects the number or fails before charging. Once signup stores the normalized value, both services agree on the stored form.

## Rollout

Each repo deploys independently, so the library must be safe to adopt one service at a time.

1. **Publish `acme-phone 1.0`** with unit tests. Include every input from the three codebases: the formats signup users type, trailing newline, leading and trailing whitespace, a bare `+`, too-short and too-long numbers, and non-string input.
2. **Support first.** It has the same semantics as billing plus strip. Replace its `valid_phone` with the library call and delete its local copy.
3. **Billing second, in shadow mode first.** Keep the old check as the decision. Also call `is_e164` and log any disagreement. Disagreements should only be the trailing-newline case. Once a week of logs is clean, switch to the library and delete the local regex. Do not add normalization inside billing. The value sent to the provider should be exactly what was validated.
4. **Signup last, since its behavior changes.** Run `normalize` alongside the loose check and log cases where the loose check accepts but `normalize` returns `None`. Review a sample of those before enforcing, because each one is either junk that was previously let through or a real user you'd start rejecting. Then switch signup to store the normalized value.
5. **Backfill existing signup records** through `normalize`, and report the ones that fail rather than deleting them.
6. **Cleanup:** remove the local `validate.py` from each repo, and add a lint or CI check that fails on a new `re.compile` for phone numbers outside the library.

**Rollback:** each service pins `acme-phone~=1.0`, so a rollback is a one-line pin change plus a redeploy. Because billing and support change last in each step and only after shadow logs are clean, a bad release can't break charging.

## Open questions (not decided here)

1. What region or regions does signup serve, and where does the region value come from (form field, IP, account country)?
2. When `normalize` returns `None` at signup, do you reject the form, or accept and flag the record because marketing wants the lead anyway?
3. Use `phonenumbers` or a hand-rolled normalizer?
4. Where does billing get its phone numbers, and are any of them stored in the loose format today? That decides how big the backfill is.
5. Do support agents type numbers or paste them from billing records? That decides whether support uses `normalize` or `is_e164`.
6. What counts as success for the migration? One suggestion is zero billing provider rejections for phone format and no drop in signup completion rate.

If you answer 1–3, I can write the library and its test cases.
