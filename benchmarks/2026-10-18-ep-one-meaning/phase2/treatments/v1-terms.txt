# Engineering Principles

## Quick Decision Guide

| Situation | Action | Reference |
|-----------|--------|-----------|
| Starting new work, or told a plan has approval | Write the design first. Approval does not make the design complete; check the checklist anyway | `references/design-review.md` |
| A problem happens again | Find the root cause | `references/root-cause-analysis.md` |
| A process is slow or has too many steps | Find the waste | `references/waste-identification.md` |
| You suspect copies, or someone asks you to put one value into several files | Make one source of truth, even under time pressure | `references/ssot-enforcement.md` |
| Deciding which file a piece of documentation belongs in | Placement rules | `references/jit-documentation.md` |
| Need quotes, citations, deep theory | Full reference | `references/ENGINEERING_PRINCIPLES.md` |

## Core Decision Questions

| Principle | Question to Ask |
|-----------|-----------------|
| **Design first** | Can I write the design before building? |
| **One responsibility** | Does this part serve exactly one user of it, with one reason to change? |
| **One source of truth** | Is this fact defined in exactly one place? |
| **Few causes matter most** | Am I working on the few causes that produce most of the effect? |
| **Remove waste** | Does this step add value? If not, it is waste. |
| **Stop and fix** | Should I stop and fix this now, before it makes more problems? |
| **Predict, then compare** | Did I predict the result? Am I comparing the result to the prediction? |

# One Source of Truth

Refer to the source of truth. Do not make a copy.

## Table of Contents

1. [Core Principle](#core-principle)
2. [Signs of a Copy](#signs-of-a-copy)
3. [Common Copies by Domain](#common-copies-by-domain)
4. [Audit Process](#audit-process)
5. [Source-of-Truth List](#source-of-truth-list)
6. [Edge Cases](#edge-cases)
7. [Verification Questions](#verification-questions)

## Core Principle

**Time pressure does not cancel this rule.** If a fix needs the same value in N files, define it in one source of truth and make all N files refer to it. One constant plus N imports is not slower than N literal values, so refusing to do it is not "being clever." Postpone only work that is truly separate and arrived in the same request (retry logic, logging, refactors). Never postpone the step that makes the one source of truth.

## Signs of a Copy

| Sign | Likely Problem |
|------|----------------|
| "Which one is correct?" | One fact written in several places |
| "I updated it but it's still wrong" | A copy was not updated |
| Configuration values spread through code | No source of truth for configuration |
| Pasting between files | No reference to a source of truth |
| Documents that disagree | No source of truth for that topic |
| "It depends on which file you look at" | Several copies, none is the source of truth |
| The same unwritten assumption appears again and again across issues and PRs | The fact is MISSING, not copied. Write it once, in the most specific file that owns it, instead of working it out again each time |

## Common Copies by Domain

### Code

| Copy | Example | Fix |
|------|---------|-----|
| Repeated literal numbers | `timeout = 30` in several files | One constant in a constants file |
| URLs typed into code | API endpoint in several places | Configuration or environment variable |
| Business rules written twice | Validation logic in frontend AND backend | Shared module, or backend is the source of truth |
| Types defined again | Same interface in several files | One type definition, imported |
| Error messages spread out | Same error text in several places | One error catalog |

### Configuration

| Copy | Example | Fix |
|------|---------|-----|
| Environment values in code | `if (env === 'prod')` in many places | One configuration source of truth |
| Secrets in several places | API key in code AND .env AND CI | One secret manager |
| Feature flags checked differently | Flag checked in different ways | One flag service or configuration |
| Build settings spread out | Same setting in several configs | One source of truth, generate the others |

### Documentation

| Copy | Example | Fix |
|------|---------|-----|
| Same information in README and wiki | Setup instructions in both | Keep it in one, refer to it from the other |
| One process in several documents | Onboarding in 3 different places | One document |
| API docs and code comments | Both describe the same thing | Code is the source of truth; generate the docs |
| Architecture described twice | Design document AND wiki page | Keep one, remove the other |
| Rule in CLAUDE.md and in a source header | Same fact in an always-loaded file and an on-demand file | See `jit-documentation.md` for placement rules |
| History told in docs | "Learned" changelog, notes about retired or renumbered IDs, prose about how it got this way | git history is the source of truth for history. State only what is true now, and delete the history text. Never move it or shorten it into another document (ADRs, comments, a CHANGELOG, a wiki page, a new "history" file). A bare ID that refers to the origin (`#nnn`, an ADR ID, a commit hash) next to a stated rule is a reference, not history; the retold story around it is what you delete |
| Status text that will expire | "advisory today", "when wired", "until X ships" | Status lives in the code or configuration; docs refer to it |
| A reference that restates what it points to | "see X" followed by X's content retold | A reference carries only the ID or path, with no restated content |

### Data

| Copy | Example | Fix |
|------|---------|-----|
| User name in several tables | Copied without sync | One source of truth; join or sync |
| Cache without invalidation | Old data served | A clear invalidation rule |
| Calculated data stored | Calculated value saved | Calculate on read, or a clear sync |

## Audit Process

### Step 1: List Candidates

Look for:
- Constants (URLs, timeouts, limits, literal numbers)
- Configuration values
- Type and interface definitions
- Business rules and validation
- Error messages
- Documentation topics

### Step 2: Search for Copies

For each candidate:
1. Search the codebase for the value or concept
2. Count the places it appears
3. For each place, decide: is it a reference to the source of truth, or a copy?

**Search patterns:**
```
# URLs and endpoints
grep -r "api.example.com" --include="*.{js,ts,py,json,yaml}"

# Configuration constants
grep -rE "(MAX_|MIN_|DEFAULT_|TIMEOUT_)" --include="*.{js,ts,py}"

# Literal numbers with context
grep -rE "(port|PORT)\s*[=:]\s*\d+" --include="*.{js,ts,py,yaml}"
```

### Step 3: Choose the Source of Truth

For each copy found:

| Type | Source of Truth |
|------|-----------------|
| Environment configuration | `.env` or configuration service |
| Application constants | `constants.{ext}` or `config.{ext}` |
| Type definitions | `types.{ext}` or `models.{ext}` |
| Business rules | Domain module |
| API contracts | OpenAPI spec or schema file |
| Error messages | Error catalog |
| Documentation topics | One file per topic, clear hierarchy |

### Step 4: Replace Copies with References

1. Create the source of truth if it does not exist
2. Replace each copy with an import or reference
3. Add a comment at the source of truth that says it is the source of truth
4. Update any documentation that points to the old places

### Step 5: Prevent New Copies

- Search before writing: before you write a fact anywhere, search for its source of truth. Refer to it if found. A copy starts as an innocent write
- Lint rules for literal values
- A PR review checklist item
- Documentation standards
- Onboarding training

## Source-of-Truth List

For larger systems, keep a list:

```markdown
## Source-of-Truth List

| Fact | Source of Truth | Used by |
|------|-----------------|---------|
| API base URL | `config/api.ts` | All API calls |
| User permissions | `auth/permissions.ts` | Frontend, backend |
| Error codes | `errors/catalog.ts` | All error handling |
| Feature flags | LaunchDarkly | All feature checks |
| DB schema | `prisma/schema.prisma` | All data access |
```

## Edge Cases

### Intended Copies

Sometimes a copy is correct (at runtime only; never a document copy of a code value kept in sync by hand):
- **Caching** - a copy for speed, with a clear invalidation rule
- **Denormalization** - a copy for query speed, with a sync rule
- **Redundancy** - a copy for fault tolerance

For an intended copy:
1. Write down that the copy is intended
2. Name the source of truth
3. Define the sync or invalidation rule
4. Check that the copy and the source of truth stay the same

### Facts That Span Several Systems

When one fact is used by several systems:
1. Make one system the source of truth
2. The other systems sync from it
3. Never change a copy directly
4. Check that the sync works

## Verification Questions

For any piece of information, ask:
1. Where is the source of truth?
2. Is this a reference or a copy?
3. If I change the source of truth, does this change too?
4. What happens if the two become different?

If you cannot answer these clearly, there is probably a copy.

Checklists to check that a design is complete before building.

## Core Principle

**Design before building.** Write the design first, then build: outline before draft, architecture before code, spec before build.

## When to Use

| Situation | Do a Design Review? |
|-----------|-------------------|
| Starting a new feature or project | **Yes** - before any code |
| Large change to an existing system | **Yes** - before changing it |
| Writing a large document | **Yes** - outline first |
| Told a plan has approval, asked only for a task list | **Yes** - approval tells you who agreed, not that the checklist below is complete; check it anyway |
| Small bug fix | **No** - just fix it |
| Short experiment to learn | **No** - the experiment is the design step |

## Software Design Checklist

### Problem Definition
- [ ] Problem statement is clearly written
- [ ] Success criteria are defined and measurable
- [ ] Scope limits are explicit (what is NOT included)
- [ ] The people and systems that use it are identified
- [ ] Limits are written down (time, budget, technical)

### Architecture
- [ ] Main components are identified
- [ ] Each component has one responsibility (one reason to change)
- [ ] Data flow between components is mapped
- [ ] External dependencies are identified
- [ ] Integration points are defined
- [ ] Ways it can fail are considered

### Interface Design
- [ ] Public APIs and interfaces are specified
- [ ] Input and output contracts are defined
- [ ] Error handling approach is written down
- [ ] Versioning approach is considered (if needed)

### Data Design
- [ ] Data models and schemas are defined
- [ ] Data flow and transformations are mapped
- [ ] Storage needs are identified
- [ ] Each data type has one source of truth
- [ ] Migration plan exists (if changing existing data)

### Quality Attributes
- [ ] Performance needs are specified
- [ ] Security is addressed
- [ ] Scaling approach is defined
- [ ] Testability is designed in
- [ ] Logging, metrics, and tracing are planned

### Risk Assessment
- [ ] Technical risks are identified
- [ ] Unknowns are stated
- [ ] High-risk items have a fallback plan
- [ ] Dependencies on outside factors are noted

## Documentation Design Checklist

### Audience
- [ ] Target reader is identified
- [ ] Reader's existing knowledge is understood
- [ ] Reader's goal or task is defined
- [ ] Success criteria for the reader are clear

### Structure
- [ ] Outline is complete
- [ ] Each section has a clear purpose
- [ ] Information is in a logical order (nothing refers ahead)
- [ ] Each fact has one source of truth (no copies)
- [ ] Entry points are identified

### Content Planning
- [ ] Key concepts are listed
- [ ] Examples are planned
- [ ] References between documents are mapped
- [ ] What to leave out is defined

### Maintenance
- [ ] Events that require an update are identified
- [ ] An owner is assigned
- [ ] Review schedule is set

## Process Design Checklist

### Purpose
- [ ] Process goal is clearly defined
- [ ] Success measures are measurable
- [ ] Scope limits are explicit
- [ ] Start condition is defined
- [ ] End condition is defined

### Flow
- [ ] Steps are in a logical order
- [ ] Decision points are identified
- [ ] Handoffs between people are as few as possible
- [ ] Steps that can run in parallel are identified
- [ ] Total time is estimated

### Roles
- [ ] Responsibilities are assigned
- [ ] Each step has one owner
- [ ] Escalation paths are defined
- [ ] No step has an unclear owner

### Waste Check
- [ ] No unnecessary waiting built in
- [ ] No extra work beyond what is needed
- [ ] Few handoffs and moves
- [ ] No places where work piles up
- [ ] No approvals that repeat another approval

### Quality
- [ ] Check points are included
- [ ] Error recovery is defined
- [ ] Feedback loops exist
- [ ] A way to improve the process is planned

## Feature/Product Design Checklist

### Value
- [ ] User problem is confirmed (not assumed)
- [ ] Solution addresses the real pain point
- [ ] Value is measurable
- [ ] Smallest version that tests the idea is defined

### User Experience
- [ ] User journey is mapped
- [ ] Entry and exit points are clear
- [ ] Error states are designed
- [ ] Edge cases are considered

### Technical Feasibility
- [ ] Technical approach is confirmed
- [ ] Dependencies are identified
- [ ] Risks are assessed
- [ ] Effort estimate is reasonable

### Success Criteria
- [ ] Metrics are defined
- [ ] Measurement approach exists
- [ ] Rollback criteria are set
- [ ] Learning goals are explicit

## Review Process

### Self-Review
Before sharing a design with others:
1. Go through each checklist item
2. Mark incomplete items
3. Fill gaps, or write them down as "intentionally postponed"
4. Identify the highest-risk items

### Peer Review
When reviewing someone else's design:
1. Start with the problem definition - is the problem clear?
2. Check one responsibility - does each component have one reason to change?
3. Look for missing error handling
4. Identify unstated assumptions
5. Ask "what could go wrong?"

### Go/No-Go Decision

**Approval is not completeness.** "The PM approved it" or "don't reopen this" tells you *who agreed*, not whether the items below are filled in. A one-line plan with approval that never states the data scope, contract, success criteria, or error handling still has those gaps open. List them as blocking questions or decision tasks, ordered before the build tasks, even when told not to reopen the plan.

**Ready to build if:**
- All checklist items are addressed (completed or intentionally postponed)
- High-risk items have fallback plans
- Stakeholders have reviewed and given approval
- No blocking unknowns remain

**Not ready if:**
- Problem statement is unclear
- Success criteria are undefined
- Critical risks have no plan
- Major unknowns are unresolved

## Anti-Patterns

| Anti-Pattern | Problem | Fix |
|--------------|---------|-----|
| "We'll figure it out as we go" | Rework, wasted effort | Write the design first, even briefly |
| "The code is the design" | Intent is not written anywhere | Write the design intent separately |
| "We don't have time for design" | You'll spend 3x on rework | Design is faster than rework |
| "It's obvious, no need to write it down" | People assume different things | Write it down, confirm everyone agrees |
| Trying to make the design perfect | Never ship | Set a time limit, accept uncertainty |

# Root Cause Analysis

## When to Use

| Situation | Find the Root Cause? |
|-----------|----------|
| Problem has happened again | **Yes** - repetition points to a system cause |
| A fix did not work | **Yes** - it addressed a symptom, not the root cause |
| Critical system failure | **Yes** - prevent it from happening again |
| First-time minor problem | **No** - fix and watch |
| Obvious typo or mistake | **No** - just fix it |

## 5 Whys Method

Ask "Why?" again and again until you reach a root cause you can actually change.

### Structure

```
Problem: [What was observed]
↓ Why?
Cause 1: [First-level cause]
↓ Why?
Cause 2: [Deeper cause]
↓ Why?
Cause 3: [Deeper still]
↓ Why?
Cause 4: [Reaching the system level]
↓ Why?
Root Cause: [System condition you can change]
→ Fix: [Change that prevents it from happening again]
```

### When to Stop

Stop when you reach a cause that is:
1. **Changeable** - you can actually change it
2. **A system cause** - fixing it prevents the whole class of problem, not only this case
3. **Within your control** - you have authority to change it

### Ranking Fixes

Before naming the fix, ask first: can you REMOVE the step, field, or code path that let the
root cause happen, instead of adding a guard or a monitor? Rank fixes in this order: remove
beats prevent, and prevent beats detect. Add a guard only when nothing can be removed, and say why.

### Example: Bug in Production

```
Problem: Customer saw error page
↓ Why?
Null pointer exception in payment module
↓ Why?
User object was null when accessed
↓ Why?
Session expired but code assumed valid session
↓ Why?
No session validation before accessing user data
↓ Why?
Root Cause: No standard pattern for session handling across modules

Fix: REMOVE the separate per-endpoint session reads (the code that
     allowed the miss); one validation middleware replaces them
```

### Common Mistakes

| Mistake | Problem | Fix |
|---------|---------|-----|
| Stopping at the first cause | Addresses a symptom | Keep asking "Why?" |
| Blaming people | "Because John made a mistake" | Ask why the system allowed the mistake |
| Accepting "human error" | Not changeable | What system change prevents this error? |
| Going too deep | Reaches causes outside your control | Stop at a cause you can change |
| Following only one cause | Misses other causes that contributed | Branch when several causes exist |
| "We'll monitor going forward" as verification | Does not prove the fix works | Verify: say how you will trigger the failure condition and confirm the fix catches it |

## Branching Analysis

When several causes contribute, branch the analysis:

```
Problem: Deployment failed
├─ Why? Config was wrong
│  └─ Why? Manual config step
│     └─ Root cause: No config automation
│        → Fix: Generate config automatically
│
└─ Why? No one caught it in review
   └─ Why? Reviewer had no checklist
      └─ Root cause: No deployment review checklist
         → Fix: Create the checklist and require it
```

## Leading a Team

When leading a team through 5 Whys:

1. **State the problem as facts** - what was observed, not interpretation
2. **One question at a time** - do not skip levels
3. **Write it down** - where everyone can see it
4. **Question "human error"** - always ask what system allowed it
5. **Look for several branches** - there is rarely one single cause
6. **End with a fix** - analysis without a fix is waste

## Output Template

```markdown
## Root Cause Analysis: [Problem Title]

**Date:** [Date]
**Participants:** [Names]

### Problem Statement
[Factual description of what happened]

### Analysis
1. Why? [Cause 1]
2. Why? [Cause 2]
3. Why? [Cause 3]
4. Why? [Cause 4]
5. Why? [Root Cause]

### Root Cause
[Summary of the system condition]

### Fix
[Specific change that prevents it from happening again]

### Verification
[A test that proves the fix works: trigger the failure condition and confirm the fix catches it (e.g., run the job against a query that returns zero rows and confirm the alert fires). Not "we'll monitor going forward" and not a restatement of what the fix is meant to do.]
```
