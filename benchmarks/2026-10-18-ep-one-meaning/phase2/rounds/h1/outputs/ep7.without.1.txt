# Postmortem: Production `order_events` table dropped, 18 Oct

**Status:** Draft | **Severity:** High | **Owner:** TBD

## Summary
While cleaning up staging tables (OPS-881), an SRE ran a `DROP TABLE` that went to the production database. It deleted `order_events`. Checkout errored from 22:15 until data was reconstructed at 01:55, about 3h40m. Restore from backup failed because backups had been failing silently. Two days of order events were only partially recovered.

## Impact
- Checkout errors from 22:15 until roughly 01:55. Confirm the exact recovery time and the error rate or number of affected orders.
- Partial permanent loss of about 2 days of `order_events`. Quantify this.

## Timeline (local time)
| Time | Event |
|---|---|
| 18:30 | An earlier prod query leaves `PGHOST=db-prod-1` exported in a shell. |
| 22:04 | Staging cleanup starts per OPS-881. |
| 22:06 | New terminal inherits the prod `PGHOST`. The prompt looks identical for prod and staging. |
| 22:07 | `DROP TABLE order_events_archive, order_events;` runs against prod. The ticket's script listed both names on one line, but only the archive table was intended. No confirmation step, and the ops role has DROP on prod. |
| 22:15 | Checkout errors spike and on-call is paged (8 min after the drop). |
| 22:41 | Cause identified (34 min after the drop). |
| 22:50 | Restore from nightly backup started. |
| 23:20 | Restore fails. The latest usable backup is 9 days old. |
| 01:55 | Data rebuilt from Kafka (7-day retention) plus the old backup. About 2 days of events are partially lost. |

## Root causes
The command was the trigger. These conditions turned one wrong command into a multi-hour outage with data loss:

1. **Nothing separated prod from staging.** Identical prompts, an inherited `PGHOST`, and no environment indicator.
2. **Routine access allowed destructive prod changes.** The ops role has DROP on prod, with no confirmation or guard.
3. **The ticket was ambiguous.** The cleanup script listed a prod-critical table beside the intended one.
4. **Backups failed silently.** The job has exited non-zero since the 3rd. Its alert went to a Slack channel that was archived in a cleanup, so nobody saw it.
5. **Slow diagnosis.** It took 34 minutes to identify the cause, with no alert tied to schema or DDL changes on prod.

## What went well
- On-call responded within minutes of the page.
- Kafka retention allowed most of the data to be rebuilt.

**Open item to verify:** "Backup failing since the 3rd" doesn't match a 9-day-old latest backup. If the incident was on the 18th, the last good backup would be about 15 days old. Check whether the backups succeeded but were unusable, or whether the date is wrong.

**What I changed from the brief:** I did not list "Dev ran the wrong command" as the root cause, and I did not name Dev or make retraining the action item. The timeline shows that any SRE with that shell would have hit prod. The outage became data loss only because backups were broken. A retraining item wouldn't have prevented either failure, and the eng org would likely read it as blaming an individual. I framed the command as the trigger and put the fixes on systems. If management wants a follow-up with Dev, it's easy to add as a non-blaming item, such as a debrief to collect their input on the tooling gaps. Do you want me to add that?
