## 4. Root cause analysis

### 4.1 The trigger is not the root cause

The proximate trigger was a query change that returned zero rows, with the manual check skipped. Calling that the root cause would be a mistake, for three reasons:

1. **Triggers vary and will keep varying.** Schema renames, credential expiry, and bad query edits have each produced this outcome. Others will follow, such as an upstream table that is late or empty, a bad join, a changed filter, or a permissions change. Fixing each trigger one at a time never ends.
2. **A manual step is a weak control.** The wiki instruction ("after changing the query, run it once by hand and eyeball the row count") depends on memory and on knowing the step exists. It also only covers one trigger, query edits. It would not have caught incidents 1 or 2, and it can't catch a failure that appears after the change.
3. **Priya joined six weeks ago.** Following an undocumented-in-practice, wiki-only step is not a reasonable expectation of a new engineer. Nothing in the review, CI, or deploy flow prompted it. Any engineer, new or experienced, can miss a step like this. A new hire hit it first.

### 4.2 Root causes (systemic)

**RC1: The job treats "zero rows" as success.**
The job exits 0 when it writes no rows. For a customer export, an empty result is almost never a legitimate outcome. The job has no notion of an expected minimum, so a total failure looks identical to success.

**RC2: Monitoring checks only the exit code.**
The only signal watched is "did the process exit non-zero." It says whether the process ran, not whether the output is correct. Given RC1, an empty file is invisible to monitoring by construction.

**RC3: No output validation gate before delivery.**
The file is delivered to the client with no check on its content, such as row count, size, or comparison against recent runs. Delivery is automatic once the job exits 0, so nothing stands between a bad file and the client.

**RC4 (contributing, incident 2): Errors are swallowed.**
The job caught the expired-credential failure and carried on to write an empty file instead of failing. That converts a loud failure into a silent one.

**RC5 (contributing, incident 3): Query changes have no automated check.**
Verification of query changes relies on a manual wiki step. There is no automated test, CI check, or review checklist item that runs the query against representative data and asserts on the result.

**RC6 (contributing): Incidents 1 and 2 did not lead to a fix for the common failure mode.**
We presumably fixed the specific trigger each time (the rename, the credential). The shared defect (RC1–RC3) stayed in place, which is why the third incident could happen. ### 4.3 Why we kept missing it: five whys

1. *Why did the client get an empty file?* The job produced one and delivered it.
2. *Why was it delivered?* The job exited 0, and delivery is gated only on exit code.
3. *Why did it exit 0 with no data?* Zero rows isn't treated as an error, and some errors are swallowed.
4. *Why didn't monitoring catch it?* It observes only the exit code, not the output.
5. *Why hasn't this been fixed after two prior incidents?* Remediation targeted each trigger rather than the shared failure mode of silent empty output. [Confirm.]
