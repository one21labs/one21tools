# Postmortem: Production order_events table dropped, partial data loss

**Date:** last night, 22:07 to 01:55
**Severity:** SEV-1 (checkout errors, permanent partial data loss)
**Status:** Resolved. Action items open.

## Summary
During a staging cleanup (OPS-881), an SRE dropped `order_events` and `order_events_archive` on the **production** database. Checkout errored for about 3h40m. The nightly backup had been failing for 9 days and nobody was alerted. We rebuilt the data from Kafka (7-day retention) plus a 9-day-old backup. About 2 days of events were partially lost.

## Impact
- Checkout errors from 22:15 until the restore finished (01:55; confirm when checkout actually recovered).
- Partial permanent loss of roughly 2 days of order events.
- Confirm before publishing: customer-facing impact numbers (failed checkouts, affected orders).

## Timeline
| Time | Event |
|---|---|
| 18:30 | SRE runs a prod query, leaving `PGHOST=db-prod-1` exported in the shell |
| 22:04 | Staging cleanup begins (OPS-881) |
| 22:06 | New terminal inherits `PGHOST=db-prod-1`. The prompt looks identical for prod and staging |
| 22:07 | `DROP TABLE order_events_archive, order_events;` runs on prod. The ticket's script listed both names on one line, and the intent was to drop only the archive table. There was no confirmation, and the ops role has DROP on prod |
| 22:15 | Checkout errors spike, on-call paged |
| 22:41 | Cause identified |
| 22:50 | Restore from nightly backup started |
| 23:20 | Restore fails. The latest usable backup is 9 days old. The backup job has exited non-zero since the 3rd, and its alert went to a Slack channel archived in a cleanup |
| 01:55 | Data reconstructed from Kafka + old backup. Two days partially lost |

## Root causes
The command was the trigger. Four independent gaps turned a mistake into a SEV-1 with data loss. Any one of them, fixed, would have prevented or sharply limited the damage.

1. **Nothing separated prod from staging.** An inherited env var silently pointed a staging session at prod, and the prompt looked the same for both.
2. **Routine credentials could destroy prod data.** The ops role has DROP on prod, and there was no confirmation step.
3. **The cleanup ticket was unsafe as written.** It listed a table that should not have been dropped (`order_events`) alongside the one that should.
4. **Backups were broken and nobody knew.** The job failed for 9 days, and its alert went to a channel that was archived. This turned a recoverable outage into data loss. We also never tested a restore.

## What went well
- On-call responded within 8 minutes of the first errors.
- Kafka retention let us recover most of the data.

## Note on retraining
I haven't listed retraining as an action item. The SRE followed a ticket, in a terminal that looked correct, with permissions we granted. Retraining wouldn't have stopped this, and it wouldn't have fixed the backup failure that caused the data loss. If management wants a training item, a team-wide session on these new guardrails fits better than one on an individual.
