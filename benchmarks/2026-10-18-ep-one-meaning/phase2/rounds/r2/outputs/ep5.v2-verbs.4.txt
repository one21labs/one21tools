```markdown
# Task Breakdown: User Data Export

Approved plan (PM, yesterday): "Build an API endpoint that exports all of a
user's data. Use whatever format is easiest. Should be fast. Ship next week."

## Phase 0: Decisions (block the build tasks; each needs a named owner)

Each item is open. Close each one with a short written answer before the
dependent build tasks start.

- [ ] D1. Data scope: which data stores and entities count as "all of a user's
      data"? Is data about the user that others own (shared records, messages,
      logs, backups, third-party processors) in or out?
- [ ] D2. Format: which format(s)? "Easiest" is not a format. Who consumes the
      file (the user, support, another system)?
- [ ] D3. Contract: request and response shape, sync or async delivery, how the
      user gets the file, how long it stays available.
- [ ] D4. Performance: what does "fast" mean, as a number? Under what data
      volume and load?
- [ ] D5. Authorization and security: who may request an export (self only,
      admins?), how identity is verified, how the file is protected in transit
      and at rest, audit logging.
- [ ] D6. Privacy and legal: is this driven by a legal requirement
      (e.g. GDPR/CCPA access requests)? Which fields must be redacted or excluded?
- [ ] D7. Success criteria: how will we know it works? What is the "done" test?
- [ ] D8. Error handling: partial failures, timeouts, oversized exports,
      retries, what the caller sees.
- [ ] D9. Abuse limits: rate limiting and size limits per user.
- [ ] D10. Rollout and rollback: flag, staged release, rollback trigger.
- [ ] D11. Ship date: "next week" assumes D1-D10 close quickly. If they don't,
      raise the date risk with the PM now, not at the deadline.

## Phase 1: Foundations (start after D1, D2, D3)

- [ ] T1. Write the one-page design: components, data flow, interface spec,
      failure modes. Capture D1-D10 answers here as the single source of truth.
- [ ] T2. Inventory data sources per D1 and name the owner of each.
- [ ] T3. Define the export schema once, in one module. The endpoint, tests and
      docs all refer to it.

## Phase 2: Build

- [ ] T4. Data collectors: one per source from T2, each with one responsibility.
- [ ] T5. Serializer for the D2 format(s), driven by the T3 schema.
- [ ] T6. API endpoint per D3 (request validation, response, status codes).
- [ ] T7. Authorization and identity checks per D5.
- [ ] T8. Error handling per D8, using a single error catalog.
- [ ] T9. Rate and size limits per D9, with values in one config file.
- [ ] T10. Audit logging, metrics and tracing for each export request.
- [ ] T11. If D3 chooses async: job queue, status endpoint, file storage and expiry.

## Phase 3: Verify

- [ ] T12. Unit tests for collectors and serializer.
- [ ] T13. Integration test: export a seeded user and compare against the T3
      schema and D1 scope. Confirm other users' data never appears.
- [ ] T14. Authorization tests: a wrong-user request and an unauthenticated
      request must fail.
- [ ] T15. Performance test against the D4 number, at realistic data volume.
- [ ] T16. Failure tests per D8: trigger each failure and confirm the behavior.

## Phase 4: Release

- [ ] T17. API documentation, generated from the T3 schema and T6 endpoint.
- [ ] T18. Rollout per D10, then compare results with the D7 and D4 targets.
```
