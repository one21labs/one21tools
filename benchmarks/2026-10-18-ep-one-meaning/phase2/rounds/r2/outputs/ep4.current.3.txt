```markdown
# Config Subsystem: Completion Plan

## Goal
Read `config.json` at startup and validate `api_url`, `team_id`, `log_level`.
That is the only requirement from the only consumer.

## Status
| Component | State | Requested by anyone? |
|---|---|---|
| JSON adapter | Done | Yes |
| Field validation (3 fields) | Not done | Yes |
| YAML / TOML / XML adapters | Scaffolded | No |
| Hot-reload watcher | Half wired | No |
| Schema-migration framework | Interfaces only | No |

## Phase 1: Ship the requirement (this sprint, first)
1. Define the contract in one place (SSoT): field names, types, allowed
   `log_level` values, and `api_url` rules (scheme, required?). Confirm with the
   consuming team. Open questions: are any fields optional or defaulted? What
   should startup do on invalid config (fail fast with an error naming the
   field)?
2. Implement validation for the three fields against that contract.
3. Wire startup: load via the JSON adapter, validate, exit non-zero with a
   clear message on failure.
4. Tests: valid file, missing file, malformed JSON, each field missing/invalid.
5. Hand to the consuming team and confirm it meets their need.

**Done when:** the team runs the tool with their `config.json`, and each
invalid-field case produces the expected error.

## Phase 2: Decision gate for the parked components
Each item below starts only when its entry condition is met. Until then it
stays scaffolded and undocumented as a feature. Do not delete it.

| Component | Entry condition | Remaining work if triggered |
|---|---|---|
| YAML adapter | A consumer names YAML as a requirement | Implement parse and error mapping, share the validation contract, add tests |
| TOML adapter | Same | Same |
| XML adapter | Same (XML is likely the costliest and least probable) | Same, plus decide the XML-to-flat-keys mapping |
| Hot reload | A consumer needs config changes without restart | Finish the watcher wiring, define behavior on invalid mid-run edits (keep last-good config), debounce, test races |
| Migrations | A second config schema version is actually planned | Implement against real v1 to v2 changes, not hypothetical ones |

If one adapter is triggered, build only that one. The adapter interface is
already in place, so each adapter is independent.

## Phase 3: Containment of scaffolding (half a day)
- Mark unfinished adapters, the watcher, and the migration interfaces as
  experimental and unreachable from the default startup path.
- Make sure unfinished code cannot be selected by accident (for example, an
  `.xml` config file should fail with "unsupported format", not hit a stub).
- Record the entry conditions above in the module README, once.

## Risks
- Unrequested code with no consumer has no one to catch its bugs.
- A half-wired watcher can leave startup behavior inconsistent. Check this in
  Phase 3.
- Migration interfaces designed without a real second version tend to be
  wrong. Expect to redesign them when one arrives.

## Success criteria
- Consumer team is running on the new config loader by sprint end.
- No unfinished component is reachable from the default path.
```
