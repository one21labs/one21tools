I wrote the root cause as the system conditions, not "Dev ran the wrong command." That command was the trigger, not the cause. Retraining Dev is not an action item here, because it wouldn't have prevented any of the three failures below. It also has no way to be verified. Postmortems that blame a person make people hide incidents, and the same setup would trap the next SRE. If management insists, I'd keep retraining as a footnote, not as the fix.

# Postmortem: Prod `order_events` tables dropped during staging cleanup

**Audience:** VP Eng, Engineering
**Status:** Draft. Owners and dates are TBD.

## Summary
During staging cleanup (OPS-881), a DROP TABLE ran against production instead of staging. This removed `order_events` and `order_events_archive`. Checkout errored from 22:15. The nightly backup was 9 days stale, so we rebuilt the data from Kafka and the old backup. The rebuild finished at 01:55, and about 2 days of events were only partially recovered.

## Impact
- Checkout errors from 22:15 until recovery (end time to be confirmed).
- About 2 days of order events partially lost.

## Timeline
| Time | Event |
|---|---|
| 22:04 | Dev starts cleanup per OPS-881. |
| 22:06 | New terminal still has `PGHOST=db-prod-1` from an 18:30 prod query. The prod and staging prompts look identical. |
| 22:07 | `DROP TABLE order_events_archive, order_events;` runs on prod. The ticket's script listed both names on one line, and the intent was only the archive table, on staging. No confirmation was asked, and the ops role has DROP on prod. |
| 22:15 | Checkout errors spike. On-call is paged. |
| 22:41 | Cause identified. |
| 22:50 | Restore from nightly backup started. |
| 23:20 | Restore fails. The latest usable backup is 9 days old. The backup job has exited non-zero since the 3rd, and its alert went to a Slack channel that had been archived. |
| 01:55 | Data rebuilt from Kafka (7-day retention) plus the 9-day-old backup. |

## Root causes
1. **Nothing distinguishes prod from staging in a shell.** Stale `PGHOST` persists across terminals, and the prompts look the same. Any engineer could have made this mistake.
2. **Routine credentials can destroy prod.** The ops role has DROP on prod, and there is no confirmation or guard on destructive statements.
3. **The cleanup ticket was unsafe.** One script line listed a prod-critical table next to the one to delete.
4. **We were blind to broken backups for 9 days.** The alert pointed at an archived channel, so nobody saw the failures. A 7-day Kafka retention also left a gap that the 9-day-old backup could not cover.

Causes 1–3 caused the outage. Cause 4 turned a short outage into a 3-hour recovery with data loss.

## Action items
Ordered by preference: remove, then prevent, then detect.

| # | Action | Type | Owner | Due |
|---|---|---|---|---|
| 1 | Remove standing DROP/TRUNCATE on prod from the ops role. Destructive DDL goes through a break-glass role with a second approver. | Remove | TBD | TBD |
| 2 | Stop exporting `PGHOST` in shells. Use named connection profiles (`psql service=staging`) that show the environment in the prompt, colored differently for prod. | Prevent | TBD | TBD |
| 3 | Cleanup tickets name one target environment and one table per statement. Add that to the ticket template. | Prevent | TBD | TBD |
| 4 | Route backup-failure alerts to the on-call pager, not a channel. Audit all alert destinations for archived channels. | Prevent | TBD | TBD |
| 5 | Run a weekly automated restore test. Alert if the newest restorable backup is older than 36 hours. | Detect | TBD | TBD |
| 6 | Set Kafka retention to at least 2× the maximum tolerated backup age, or move to PITR/WAL archiving. | Prevent | TBD | TBD |

## Verification
- **#1:** Run a DROP as the ops role on prod. It must be denied.
- **#2:** Open a fresh terminal. `PGHOST` must be unset, and the prod prompt must visibly differ.
- **#4:** Force the backup job to fail in a test. The on-call must be paged.
- **#5:** Delete a test backup. The age alert must fire, and the restore test must fail loudly.

## Open items before publishing
- The dates don't line up. "Failing since the 3rd" and "9 days stale" only match if the incident was on the 12th, but the incident was last night. Confirm the real failure start date, because it sets how long the backup was silently broken.
- Add the checkout recovery time and a count or estimate of the lost events.
- Assign owners and dates.
