## Why the plan doesn't complete the adapters, watcher, and migrations

The one team that uses the tool needs `config.json` read at startup with three fields validated. The JSON adapter already does the reading. Nobody has asked for YAML, TOML, XML, hot reload, or migrations. Finishing them would take most of the sprint and add three subsystems to test and maintain, with no user.

The two weeks already spent are gone whether or not you finish this work. Finishing it only adds cost on top of that. The scaffolding also stays in git history, so removing it from the tree loses nothing.

If a second team later needs YAML, you can restore the adapter scaffold from git history. By then you'll know the real requirement, and that should produce a better design than the one you have now.

## Proposed `plan.md`

```markdown
# Config Subsystem: Sprint Completion Plan

## Problem
The CLI must read config.json at startup and validate api_url, team_id,
and log_level. This is the only requirement, from the one team that uses the tool.

## Success criteria
- Startup loads config.json and fails fast with a clear error on a missing
  file, invalid JSON, or an invalid field.
- Each of the three fields has a documented validation rule.
- Tests cover: valid config, missing file, malformed JSON, and each field
  missing or invalid.

## Out of scope (removed, not deferred)
- YAML / TOML / XML adapters
- Hot-reload file watcher
- Schema-migration framework
Nobody has requested these. The code is deleted from the tree. Git history
is the record if a real need appears.

## Open questions (answer before building)
1. api_url: which schemes are allowed (https only?), and must it be reachable?
2. team_id: what format (string, integer, pattern)?
3. log_level: the allowed set, and is it case-sensitive?
4. Config file location: fixed path, CLI flag, or env var?
5. Error behavior: exit code and message format on failure.

## Tasks (in order)
1. Resolve the open questions with the consuming team.
2. Define the validation rules once, in one module. This is the single
   source of truth for field rules; docs and error messages refer to it.
3. Remove the YAML/TOML/XML scaffolds, the watcher, and the migration
   interfaces from the tree.
4. Collapse the adapter layer: if JSON is the only format, the read call
   goes directly to the JSON parser. No adapter interface is needed.
5. Implement startup load plus validation using the rules from task 2.
6. Write the tests listed under success criteria.
7. Demo to the consuming team and confirm it meets their requirement.

## Risks
- The team's requirement may change. Mitigation: ask in task 1 whether
  they expect other formats. Build for the answer, not for a guess.
```
