```markdown
# Config Subsystem: Completion Plan

## Problem and success criteria
The one consuming team needs the CLI to read `config.json` at startup and validate
`api_url`, `team_id` and `log_level`.

Done when:
- The CLI loads `config.json` at startup and exits non-zero with a clear message on any invalid or missing field.
- Each of the three fields has tests for a valid value and each failure case.
- The consuming team confirms it works with their real config.

## Out of scope
YAML/TOML/XML formats, hot reload, schema migrations. None are requested.
They are removed in step 4, not completed.

## Open questions (answer before step 2)
These are open. Nothing here has a default yet.
1. `api_url`: which schemes are allowed (https only?), and is a trailing slash normalized?
2. `team_id`: what is its type and format (string, integer, pattern)?
3. `log_level`: what is the allowed set, and is matching case-sensitive?
4. Missing `config.json`: fail, or fall back to defaults? Where is the file looked up?
5. Unknown extra fields: reject, warn, or ignore?
6. Error output: message format, exit codes, and whether all errors are reported or only the first.

## Tasks
1. **Resolve the open questions** with the consuming team. Record the answers as the validation rules, in one schema definition. Nothing else restates them (one source of truth).
2. **Implement load and validate** on the finished JSON path. One entry point, called at startup.
3. **Tests**: valid config, each field missing, each field invalid, malformed JSON, missing file, unknown fields (per answer to Q5).
4. **Remove unrequested code**: delete the YAML/TOML/XML adapters, the file watcher, and the migration interfaces. Then check whether the pluggable adapter layer still has any reason to exist with one format. If not, delete it and read JSON directly.
5. **Verify with the consuming team** using their real config. Also trigger each failure case on the real CLI and confirm the exit code and message.

## Risks
- The consuming team's real config may contain values the rules reject. Step 5 catches this.
- Deleting the adapter layer may touch call sites. Search all usages before removing.

## Review trigger for the removed features
Reintroduce a format, hot reload or migrations only when a team asks for it and names the use case.
```
