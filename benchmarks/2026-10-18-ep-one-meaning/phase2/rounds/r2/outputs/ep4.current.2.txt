```markdown
# Config Subsystem Completion Plan

## Goal
Finish the config subsystem this sprint. Order of work: the real requirement
first, then the architecture already scaffolded.

## Real requirement (the only one with a consumer)
Read `config.json` at startup and validate `api_url`, `team_id`, `log_level`.

## Phase 0: Ship the requirement (Day 1-2)
- [ ] Confirm the JSON adapter loads config.json end to end
- [ ] Implement validation for the three fields
      - api_url: valid URL, scheme allowed (decide: https only?)
      - team_id: non-empty, format (decide)
      - log_level: enum (decide values; default?)
- [ ] Define error contract: missing file, bad JSON, invalid field
      (message, exit code). One place defines this.
- [ ] Tests for each failure mode
- [ ] Release to the team. Acceptance: team runs the CLI with their config.

Definition of done for the sprint is Phase 0 shipped. Everything below is
additive and must not block it.

## Open design questions (answer before building Phases 1-3)
| Question | Needed for | Owner | Answer |
|---|---|---|---|
| Who will use YAML/TOML/XML configs, and when? | Phase 1 | | |
| Who needs hot reload? Which fields are safe to change at runtime? | Phase 2 | | |
| What config version exists today? What v2 change forces a migration? | Phase 3 | | |
| Who owns maintenance of these after the sprint? | All | | |

If a question has no answer, the phase it gates is timeboxed as below, then
parked. Don't leave it half-built.

## Phase 1: Format adapters (Day 3-5)
Order: TOML, YAML, XML (by how likely a team would actually adopt them).
For each adapter:
- [ ] Implement parse into the same internal model the JSON adapter produces
- [ ] Run the same Phase 0 validation. Do not duplicate validation per adapter.
- [ ] Shared adapter conformance test suite: one fixture set, run against
      every adapter, so behavior is identical across formats
- [ ] Format selection rule (file extension vs explicit flag), written once
- [ ] Decide XML scope: attributes vs elements mapping, or drop XML
Exit: all adapters pass the conformance suite.

## Phase 2: Hot reload (Day 6-8)
- [ ] Finish wiring the file watcher (inventory what is currently wired)
- [ ] Define reload semantics: atomic swap of validated config only;
      on validation failure keep the old config and log the error
- [ ] Debounce, handle editor save-via-rename, and handle file deletion
- [ ] Define which fields are reloadable (api_url change mid-run?)
- [ ] Subscriber/notification mechanism for consumers
- [ ] Tests: valid change, invalid change, rapid writes, delete/recreate
- [ ] Verification: inject an invalid edit and confirm the running config is
      unchanged and an error is logged
Exit: reload verified by the failure-injection test above.

## Phase 3: Migration framework (Day 9-10)
- [ ] Define the version field and its default for existing unversioned files
- [ ] Implement migration chain (v1 -> v2 -> ...) over the interfaces already
      defined
- [ ] At least one real migration, or the framework has no consumer
      (if none exists, ship with an identity migration and stop)
- [ ] Tests: upgrade path, unknown future version, migration failure
- [ ] Migration runs before validation. Validation stays the single check.

## Cross-cutting rules
- Single source of truth: field names, log_level values, and defaults are
  defined once (one schema/constants module) and imported everywhere,
  including every adapter and migration.
- Documentation: one doc for config format and behavior, linked from README.
  No duplicate copies.
- No new features beyond this plan.

## Risks
- Unrequested surface area: 3 formats, a watcher and migrations all need
  ongoing maintenance with no current user. Mitigation: shared test suite,
  single validation path.
- Schedule: Phases 1-3 are ~8 days on a sprint that also has to ship Phase 0.
  Mitigation: timeboxes above; unfinished phases are parked, not extended.
- Half-wired watcher is the highest-risk code (concurrency, partial reads).

## Decision gates
- End of Phase 0: shipped? If not, stop all other work.
- End of each later phase: did the open question get an owner/answer?
  If not, park the remaining scope.
```
