The plan doesn't define a few things the build depends on, so I made them short decision tasks at the top, ahead of the build tasks. Each should take minutes, not a meeting.

```markdown
# User Data Export: Implementation Tasks

Plan (approved): Build an API endpoint that exports all of a user's data. Use whatever format is easiest. Should be fast. Ship next week.

## Phase 0: Decisions (blocking; owner and answer recorded here, each ~15 min)

- [ ] D1. Scope of "all of a user's data": list every table/store holding user data (including third-party and derived data). Record the list here as the single source of truth. Mark each in or out of scope.
- [ ] D2. Format: pick one (recommend JSON, since it is the easiest and handles nested data). Record it here.
- [ ] D3. "Fast" target: set a measurable number (e.g. p95 response time for a typical user, and the largest user's data size). Without one, the performance work can't be checked.
- [ ] D4. Delivery mode: synchronous download vs. async job + link. Decide from the D3 numbers and the largest user's data size.
- [ ] D5. Authorization: who may call this (the user for their own data only? admins?). Confirm whether it's tied to a legal requirement (GDPR/CCPA access request), which affects scope and audit needs.
- [ ] D6. Sensitive fields: decide what is excluded or redacted (password hashes, tokens, other users' data in shared records).
- [ ] D7. Ship criteria: define "done" and the rollback condition for next week's release.

## Phase 1: Design (small, written down)

- [ ] T1. Write the endpoint contract: route, method, auth, request params, response schema, status codes. Link D2 and D4 rather than restating them.
- [ ] T2. Define the error handling: unauthenticated, unauthorized, user not found, partial failure, timeout, rate limit.
- [ ] T3. Define the export schema in one place (a schema file or type) to serve as the source of truth for both the code and the docs.

## Phase 2: Build

- [ ] T4. Implement a data collector per store from D1. Each collector has one job, returns its section of the export, and is registered in one list.
- [ ] T5. Implement the export assembler that combines the collectors' output into the T3 schema, applying the D6 exclusions.
- [ ] T6. Implement the endpoint with authentication and authorization (D5), so a user can only export their own data.
- [ ] T7. Apply the D4 delivery mode: streaming/pagination for synchronous, or job + status + expiring download link for async.
- [ ] T8. Add rate limiting and an audit log entry for each export request.
- [ ] T9. Implement the T2 error handling.

## Phase 3: Verify

- [ ] T10. Unit tests: each collector, the assembler, and redaction (D6).
- [ ] T11. Authorization tests: user A cannot export user B's data; unauthenticated calls are rejected.
- [ ] T12. Completeness test: for a seeded test user with data in every D1 store, the export contains it all.
- [ ] T13. Performance test against the D3 target, using the largest realistic user.
- [ ] T14. Failure tests: one store down, timeout, and oversized export each produce the T2 behavior.

## Phase 4: Ship

- [ ] T15. Document the endpoint (generated from the T3 schema, not hand-copied).
- [ ] T16. Deploy behind a feature flag; smoke-test in staging.
- [ ] T17. Release against the D7 criteria; confirm the rollback path works.
```

D1, D3, D5 and D6 have the most effect on whether you ship next week. A wrong "all data" list or a missing authorization check in an export endpoint is a data-exposure problem, not just a bug.
