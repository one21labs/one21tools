I'm not reopening the plan. But "approved" tells us who agreed, not that the plan is complete. The plan never states the data scope, format, auth, or what "fast" means. Those are decisions, not rework, and the build tasks depend on them. They come first as short decision tasks, so they don't turn into rework mid-week. Most can be settled in one message to the PM.

```markdown
# User Data Export: Implementation Tasks

Approved plan: "Build an API endpoint that exports all of a user's data. Use whatever format is easiest. Should be fast. Ship next week."

## Phase 0: Decisions (blocking, do first, target: day 1)
Each needs a one-line written answer. Record answers in this file.

- [ ] D1. Data scope: which tables/stores count as "all of a user's data"? (Include derived data, logs, third-party-held data?) Output: a list of data sources.
- [ ] D2. Exclusions: anything that must NOT be exported (other users' data, internal flags, secrets, password hashes)?
- [ ] D3. Format: pick one (JSON is the easiest default; confirm it satisfies any legal/GDPR portability need). Output: chosen format.
- [ ] D4. Authorization: who can request an export? (The user for their own data only? Admins?) Is re-authentication required?
- [ ] D5. "Fast" target: a measurable number (e.g. p95 response time for a typical user, largest expected user size). This decides sync vs. async in B1.
- [ ] D6. Delivery: synchronous download, or async job plus a link/email?
- [ ] D7. Success criteria and rollback: how do we know it works, and when do we turn it off?
- [ ] D8. Rate limits: how many exports per user per period?

## Phase 1: Design (short, one page, target: day 1-2)
- [ ] T1. Write the contract: endpoint path, method, request, response shape, error codes (auth failure, rate limit, too large, timeout). Based on D3, D4, D6.
- [ ] T2. Map each data source from D1 to its query/owner. Name one source of truth per data type; do not copy fields into a separate export schema by hand.
- [ ] T3. Sync vs. async decision from D5 and measured data size (see T4). Record it.

## Phase 2: Build (target: day 2-4)
- [ ] B1. Implement the endpoint skeleton with the authentication and authorization from D4.
- [ ] B2. Implement one collector per data source in T2, using the shared models/types (no duplicated schemas).
- [ ] B3. Apply the exclusions from D2 in one central place (an allow-list preferred over a deny-list).
- [ ] B4. Serialize to the chosen format (D3), streaming if large.
- [ ] B5. Rate limiting (D8).
- [ ] B6. Error handling and timeouts per the T1 contract.
- [ ] B7. Audit log: record who exported what and when.
- [ ] B8. If async (T3): job queue, status endpoint, expiring download link.

## Phase 3: Verify (target: day 4-5)
- [ ] V1. Tests: user A cannot export user B's data; unauthenticated is rejected; excluded fields never appear.
- [ ] V2. Completeness test: every data source in D1 appears in the output.
- [ ] V3. Performance test against the D5 target, using the largest realistic account.
- [ ] V4. Rate limit and error-path tests.

## Phase 4: Ship (target: day 5)
- [ ] S1. Behind a feature flag, with the rollback criteria from D7.
- [ ] S2. API docs generated from the contract in T1 (not hand-written copies).
- [ ] S3. Deploy, then run one real export end to end and compare it against the expected data.
```

The two decisions most likely to hurt the schedule are D1 (scope) and D5 (the "fast" number). A wrong guess on either changes the architecture, so I'd ask the PM those two today.
