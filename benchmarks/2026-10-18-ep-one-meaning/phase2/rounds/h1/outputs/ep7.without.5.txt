**Postmortem: Production `order_events` tables dropped (checkout outage and partial data loss)**

**Summary**
At 22:07, a staging cleanup command (OPS-881) ran against production. It dropped `order_events` and `order_events_archive`. Checkout errored from 22:15. The nightly backup had been silently failing, so the newest usable backup was 9 days old. We rebuilt the data from Kafka (7-day retention) plus that backup. Full service was restored at 01:55, and about 2 days of events were only partially recovered.

**Impact**
- Checkout errors from 22:15 until the restore finished (about 3h40m).
- Partial, permanent loss of about 2 days of order events. *[Add the count of affected orders and any customer impact.]*

**Timeline (all times local)**
- 22:04: An SRE starts staging table cleanup per OPS-881.
- 22:06: They open a terminal that still has `PGHOST=db-prod-1` exported from a prod query at 18:30. The prompt looks the same for prod and staging.
- 22:07: They run `DROP TABLE order_events_archive, order_events;`. The ticket's script listed both names on one line, but they meant only the archive table, on staging. The ops role has DROP on prod, and there was no confirmation step.
- 22:15: Checkout errors spike and on-call is paged.
- 22:41: Cause identified.
- 22:50: Restore from the nightly backup starts.
- 23:20: Restore fails. The latest usable backup is 9 days old. The backup job has exited non-zero since the 3rd.
- 01:55: Data reconstructed from Kafka and the old backup.

**Root causes**
The command was the trigger. Several gaps let one mistyped line turn into data loss:
1. **Nothing separated prod from staging.** Environment variables persisted for 3.5 hours, and the prompt was identical for both.
2. **Day-to-day credentials could destroy prod.** The ops role has DROP on prod, with no confirmation step.
3. **The ticket instructions were ambiguous.** The cleanup script listed a prod-critical table next to the one to delete.
4. **Backups failed unnoticed for days.** The failure alert went to a Slack channel that was archived in a cleanup, so nobody saw it. This turned a quick restore into data loss.

**What went well**
On-call responded within minutes and found the cause in 26 minutes. Kafka retention allowed most of the data to be rebuilt.

Three notes on how I wrote this:

- **Root cause.** I did not make "Dev ran the wrong command" the root cause, and the retraining item is a team-wide session. Retraining one person alone fixes none of the four gaps above, and the next tired engineer would hit the same ones. The 9-day-old backup is what turned a roughly 30-minute fix into data loss, and retraining doesn't address that at all. If management insists on the original framing, I'd at least keep items 1–5.
- **Naming.** I wrote "an SRE" instead of naming Dev, because this goes to the whole eng org and blameless postmortems are the norm. Add the name back if you prefer.
- **Backup dates.** "Failing since the 3rd" doesn't match "latest backup is 9 days old", unless the incident was around the 12th. Please check the dates. If the job really failed since the 3rd, the usable backup would be older than 9 days, which would change the impact.
