```markdown
# Config Subsystem: Completion Plan

## Requirement (the only one)
Read `config.json` at startup and validate three fields: `api_url`, `team_id`, `log_level`.
Source: the one team that uses the tool. Nobody has asked for anything else.

## Decision: remove, don't complete
These are unrequested, so finishing them is waste, not progress:

| Item | State | Decision | Why |
|------|-------|----------|-----|
| YAML / TOML / XML adapters | scaffolded | Remove | No user. Each adds parsing deps, tests, and bugs to maintain. |
| Hot-reload watcher | half wired | Remove | No user. Reload mid-run adds races and partial-read states. Startup read is the requirement. |
| Schema-migration framework | interfaces only | Remove | There is exactly one config version. Nothing exists to migrate from. |
| Format-adapter abstraction | JSON finished | Collapse to a direct JSON load | One format needs no plugin layer. |

The two weeks already spent are sunk cost. Finishing the work would add roughly 3x more
unused code to maintain. Removing it now costs less than carrying it.
If one of these becomes a real request later, git history has the scaffolding.
Don't leave it commented out or parked in the tree.

## Open questions (answer before building)
These gaps are unanswered in the current design:
1. Allowed `log_level` values (e.g. debug/info/warn/error)? Case-sensitive?
2. `api_url` rules: scheme required (https only?), trailing slash handling?
3. `team_id` type and format: string or integer, any pattern or length limit?
4. Missing file: fail, or fall back to defaults? Which exit code and message?
5. Malformed JSON, missing field, or wrong type: one error listing all problems, or fail on the first?
6. Unknown extra fields: ignore, warn, or reject?
7. Config file location: fixed path, CLI flag, or env var?
8. Success criteria: what does "done" look like to the team that uses it?

## Tasks (in order)
1. Get answers to the open questions above from the team. Write them into the schema (task 2).
2. Define the three-field schema in one place. This is the single source of truth for field rules,
   error messages, and allowed values. Docs and tests refer to it and don't restate it.
3. Delete the YAML, TOML, and XML adapter scaffolds and their dependencies.
4. Delete the watcher code and its wiring.
5. Delete the migration interfaces.
6. Replace the adapter layer with a direct `config.json` load plus validation against the schema.
7. Error handling: implement the behavior chosen in questions 4-6, with clear messages naming the field.
8. Tests: valid config; each field missing; each field wrong type or value; file missing; malformed JSON.
9. Verify against a real `config.json` from the requesting team's setup.

## Done when
- Tool starts with a valid `config.json`.
- Every invalid case in task 8 fails with a clear message and the agreed exit code.
- No unused adapters, watcher, or migration code remains in the tree.

## Risks
- Team later wants another format or reload: handle as a new request with its own design, using the real use case.
```
