```markdown
# Config Subsystem: Completion Plan

## Problem and requirement
The one consuming team needs the CLI to read `config.json` at startup and validate
three fields: `api_url`, `team_id`, `log_level`. This is the only requirement.

## Current state (about half done)
| Component | State | Requested by anyone? |
|-----------|-------|----------------------|
| Adapter architecture + JSON adapter | Done | Yes (JSON) |
| YAML / TOML / XML adapters | Scaffolded | No |
| Hot-reload watcher | Half wired | No |
| Schema-migration framework | Interfaces only | No |
| Validation of the 3 fields | **Unconfirmed** | Yes |

## Success criteria
- CLI starts with a valid `config.json` and exposes the three fields.
- Invalid or missing file, missing field, or bad value exits non-zero with a
  message naming the file, field and reason.
- Tests trigger each failure: missing file, malformed JSON, each field
  missing, each field wrong type or value.

## Scope
In: Phase 1 below.
Out until the Phase 2 gate passes: YAML/TOML/XML, watcher, migrations.

## Phase 1: ship the requirement (this sprint)
1. Confirm the validation rules with the consuming team and write them down in
   one place (the schema definition is the source of truth; docs and errors
   refer to it, no restated copies):
   - `api_url`: valid URL? https only?
   - `team_id`: format and type?
   - `log_level`: allowed set (e.g. debug/info/warn/error)?
2. Implement validation over the JSON adapter's output.
3. Wire into CLI startup. Define the error contract (message, exit code).
4. Write the failure-condition tests listed above.
5. Release to the consuming team and get their confirmation.

## Phase 2 gate (decide at sprint review, not now)
Build an item only if a named user or team requests it. Record who and when.
| Item | Build when |
|------|-----------|
| YAML / TOML / XML adapter | A team has a config in that format |
| Hot reload | A team needs changes without a restart |
| Migrations | A second config version exists that must be upgraded |

## Phase 2 work (only for items that pass the gate)
Each item gets its own short design (interface, errors, success criteria,
tests) before code.

### Adapters (per format, about 1-2 days each)
- Finish the parser against the existing adapter interface.
- Same validation as JSON: all adapters feed one schema, with no per-format rules.
- Tests: valid file, malformed file, each field failure, and a parity test that
  the same data in every format gives the same result.
- XML needs an extra decision: how attributes and repeated elements map to
  fields.

### Hot-reload watcher (about 3-5 days)
- Open decisions: which fields may change live, what happens on an invalid
  reload (keep last good config and log), debounce and atomic-save handling,
  and how consumers get notified.
- Tests: valid change applies, invalid change is rejected and the old config
  is kept, rapid successive writes, file deleted mid-run.

### Migrations (about 3-5 days)
- Blocked until a real second schema version exists. Without one, the
  migration steps can't be specified or tested.
- Decide: where the version lives in the file, the policy for files that are
  too new, and whether to rewrite the file or migrate in memory.
- Tests: each step v(n) to v(n+1), a chained upgrade, an unknown version.

## Risks
- Maintenance cost of unused code paths (parsers, watcher threads, migration
  steps), each with its own bugs and dependencies.
- Unspecified behavior in the scaffolds (reload semantics, XML mapping,
  migration policy) means estimates above are low-confidence.

## Open questions (blocking Phase 1)
1. What are the exact validation rules for the three fields?
2. What should the CLI do on invalid config: exit code and message format?
3. Is the Phase 1 validation already implemented, and where?
```
